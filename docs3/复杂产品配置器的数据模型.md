## 一、总体数据模型（核心实体及关系）

### 1.1 建模边界与核心结论

电商产品（手机数码等）可以用 **Category -> SPU -> SKU** 三层模型覆盖，因为其核心问题是「选哪个颜色/容量组合」，SKU 是最终可售单元。

复杂产品（服务器、工业设备、PLC 配置器）不同。它的核心问题是：

- 产品由多级部件组成（CPU、内存、硬盘、电源、支架...）
- 每个部件分类下有多个候选 Part
- Part 之间存在数量、兼容、依赖、计算、优选等多种约束规则
- 同一产品平台可派生出多个可售型号（低端 S1110、高端 S22）
- 客户需要通过配置器选择组合，系统校验约束后输出 BOM/报价/交付规格

因此，复杂产品配置需要 **双层元模型 + 三层实例** 的结构：

| 层次 | 解决的问题 | 核心对象 | 典型责任人 |
| --- | --- | --- | --- |
| **L0 平台基础元模型** | 平台能够定义什么类型的对象、属性和关系 | OntoObjectType、OntoAttrType、OntoLinkType | 平台架构师、IT、FDE |
| **L1 业务元模型** | 产品领域允许定义哪些业务类型及语义 | ProductClassType、PartClassType、ProductInstanceType | IT 与公司级业务/行管人员 |
| **L2 业务对象实例** | 某产品平台的骨架是什么，可售型号如何裁剪 | ProductClass、PartClass、Part、ProductInstance | 产品数据架构师、产品数据工程师 |
| **L3 配置运行实例** | 客户本次选择什么，是否有效，输出什么 | Configuration、ConfiguredPart、ConstraintEvaluation | 销售、客户、配置引擎 |

### 1.3 详细实体关系表

#### L0 平台基础元模型

| 实体名称 | 英文名 | 定义 | 关键字段 | 关联关系 |
|---------|--------|------|---------|---------|
| **对象类型** | OntoObjectType | 可被实例化的对象类型 | id, code, name, version, abstract, parent_type_id, lifecycle_type_id | 1:N → OntoAttrType；N:M → OntoLinkType |
| **属性类型** | OntoAttrType | 对象属性的类型、基数和值域定义 | id, code, data_type, cardinality, required, unit_type, value_domain | N:1 ← OntoObjectType |
| **关系类型** | OntoLinkType | 对象之间的有向关系类型 | id, code, source_type_id, target_type_id, cardinality, inverse_code, composition | 关联源/目标 OntoObjectType |
| **扩展Schema** | ExtensionSchema | 指定对象可挂载的扩展字段组 | id, code, applies_to_type, namespace, version, fields[] | N:M → OntoObjectType |
| **生命周期类型** | LifecycleType | 状态、迁移和发布门禁定义 | id, code, states[], transitions[] | 1:N → OntoObjectType |

#### L1 业务元模型

| 实体名称 | 英文名 | 定义 | 关键字段 | 关联关系 |
|---------|--------|------|---------|---------|
| **产品类元模型** | ProductClassType | 产品族或产品平台类型，承载平台化和标准化 | code, name, domain, modeling_policy | composedOf → PartClassType |
| **部件类元模型** | PartClassType | 可配置子模块的抽象，如 CPU、硬盘、显示器 | code, name, part_kind, selection_policy, min/max_cardinality | hasSpec → SpecDefinition；contains → PartClassType |
| **规格定义** | SpecDefinition | 属性或规格定义 | code, name, data_type, unit, value_domain, required | definedOn → ProductClassType/PartClassType |
| **可售产品元模型** | ProductInstanceType | 可售产品定义，如 S1110、S22 | code, name, market, status, effective_period | realizes → ProductClassType |

#### L2 业务对象实例

| 实体名称 | 英文名 | 定义 | 关键字段 | 关联关系 |
|---------|--------|------|---------|---------|
| **产品模型** | ProductClass | 产品族或平台的可复用骨架 | id, code, name, version, status | 1:N → PartClass；1:N → ConstraintRule |
| **部件分类** | PartClass | 可配置子模块的分类边界 | id, code, name, product_class_id, selection_policy, min_qty, max_qty, multi_instance | N:1 ← ProductClass；1:N → Part |
| **部件** | Part | PartClass 的具体实例，如一个明确编码的 CPU 或硬盘 | id, code, name, part_class_id, status, price | N:1 ← PartClass；1:N → SpecValue |
| **规格值** | SpecValue | 部件的具体规格属性值 | id, part_id, spec_code, value, unit | N:1 ← Part |
| **产品实例** | ProductInstance | 确定销售边界的可售产品（对标电商 SPU） | id, code, name, product_class_version_id, market, status | realizes → ProductClassVersion；N:M → Part |
| **规格覆盖** | SpecOverride | 产品实例相对于模型的规格差异 | id, product_instance_id, spec_code, override_value, reason | N:1 ← ProductInstance |

#### L3 配置运行实例

| 实体名称 | 英文名 | 定义 | 关键字段 | 关联关系 |
|---------|--------|------|---------|---------|
| **配置方案** | Configuration | 一次客户配置方案 | id, product_instance_id, model_snapshot_id, status, customer_context | N:1 ← ProductInstance |
| **已选部件** | ConfiguredPart | 已选 Part、实例号和数量 | configuration_id, part_id, instance_no, quantity, selected | N:1 ← Configuration, Part |
| **已选属性值** | ConfiguredValue | 本次输入或属性值 | owner_type/id, spec_or_parameter_id, value, unit | N:1 ← Configuration |
| **约束评估** | ConstraintEvaluation | 规则评估结果 | rule_id, passed, severity, message | N:1 ← Configuration |
| **配置解** | ConfigurationSolution | 引擎候选解或推荐解 | rank, objective_values, selected_parts[], explanation | N:1 ← Configuration |

## 四、新模型与 cruleengine 现有模型的关系

### 4.1 定位说明

新模型是 **数字产品全生命周期的业务事实模型**；cruleengine 主要是 **配置约束的声明和执行模型**。

二者是「业务事实源 → 可执行投影」关系：

```
数字产品模型（源）              cruleengine 执行模型（投影）
─────────────────              ───────────────────────────
ProductClassVersion  ──compile──> Module
PartClass            ──compile──> PartCategory
Part + SpecValue     ──compile──> Part + dynAttr
InputParameter       ──compile──> Para
ConstraintRule       ──compile──> Rule / RuleSchema / algorithm
Configuration        <──result─── ModuleInst
ConfiguredPart       <──result──> PartInst / PartCategoryInst
```

### 4.2 概念映射表

| 新建模概念 | cruleengine 概念 | 关系和差异 |
| --- | --- | --- |
| ProductClassVersion | Module | Module 含版本、PartCategory、Part、Para 和 Rule，是执行投影 |
| PartClass | PartCategory | 均表达候选分类；现有类已有 selectionPolicy、supportMultiInst 和递归结构 |
| Part | Part | 基本一致；业务层还需物料主数据、有效期、供应和销售状态 |
| SpecDefinition | DynamicAttribute | 均支持类型和选项；业务层还需单位、值域、治理和版本 |
| SpecOption | DynamicAttributeOption | 对应选项编码和值 |
| InputParameter | Para | 对应输入、计算和汇总参数 |
| ConstraintRule | Rule + RuleSchema | 业务规则编译为可执行 Schema 或算法 |
| ConfigurationSolution | ModuleInst | ModuleInst 承载数量、优先级值和分类实例 |
| ConfiguredPart | PartInst | 对应 quantity、selected、hidden 和选中属性 |
| ExtensionValue | Extensible.extSchema/extAttrs | 可作运行载体，但业务层仍需 Schema 注册和治理 |

### 4.3 MultiPCTest 样例映射

基于 `MultiPCTest.java` 中的 `MultiPCConstraint` 类：

| 新建模 | cruleengine | 示例 |
| --- | --- | --- |
| PartClass: drive | PartCategoryVar drive | 硬盘部件分类 |
| PartClass: cpu | PartCategoryVar cpu | CPU部件分类 |
| SpecDefinition: Speed | @DAttrAnno(code = "Speed", ...) | 转速属性 |
| SpecDefinition: Capacity | @DAttrAnno(code = "Capacity", ...) | 容量属性 |
| SpecDefinition: CoreNum | @DAttrAnno(code = "CoreNum", ...) | 核心数属性 |
| SpecDefinition: Memory | @DAttrAnno(code = "Memory", ...) | 内存容量属性 |
| Part: sd1, sd2, sd3 | @PartAnno(fatherCode = "drive", ...) | 固态硬盘实例 |
| Part: md1, md2, md3 | @PartAnno(fatherCode = "drive", ...) | 机械硬盘实例 |
| Part: cpu1, cpu2, cpu3, cpu4 | @PartAnno(fatherCode = "cpu", ...) | CPU实例 |
| ConstraintRule: R_CPU_DRIVE_01 | @CodeRuleAnno(logicAB1) | 跨分类不兼容规则 |
| ConstraintRule: R_CPU_01 | @CodeRuleAnno(logicA1) | 选择基数规则 |
| ConstraintRule: R_DRIVE_01 | @CodeRuleAnno(logicB1) | 实例数量规则 |
| ConstraintRule: R_DRIVE_02 | @PriorityRuleAnno(logicB2) | 优选规则 |
| ConfigurationSolution | inferRecommendModule() | 配置求解入口 |
| ConfiguredPart | ModuleInst 输出 | 包含 Q(quantity), H(hidden), S(selected) |

### 4.4 需要保持的边界

1. **Module 不应兼任产品主数据仓库**。应由编译或适配层从已发布业务模型生成 ProductClassVersion。

2. **现有 Part.price 只是单值**，不足以承载币种、区域、渠道、阶梯和有效期定价。业务模型应引用独立定价域。

3. **extAttrs 适合传递已知 Schema 的扩展值**，不应替代属性定义、校验、索引、权限和版本管理。

4. **ProductInstance 可编译成裁剪后的 Module**，也可使用基础 Module 加候选集过滤输入。需通过性能和版本隔离测试选择。

5. **模型升级需要快照机制**。历史报价和 BOM 必须能够复现，不能因为模型变更导致历史配置无法验证。

### 4.5 实施建议

| 阶段 | 任务 | 说明 |
| --- | --- | --- |
| **Phase 1** | L0 类型注册和实例存储 | 先实现 OntoObjectType/AttrType/LinkType 的注册、存储、Schema 校验和版本机制 |
| **Phase 2** | L1 产品领域类型注册 | 注册 SERVER_X86 产品类及 cpu/drive 部件类元模型 |
| **Phase 3** | L2 产品模型设计 | 以 CPU + drive 为首个纵向切片，跑通 ProductClass、Part、ConstraintRule |
| **Phase 4** | 编译器开发 | 建立 ProductClassVersion → Module 的单向编译器 |
| **Phase 5** | ProductInstance 裁剪 | 实现 S1110/S22 实例化，与 MultiPCTest 数据对齐 |
| **Phase 6** | 配置求解验证 | 将「同一配置输入 + 同一快照 = 同一结果」作为基础验收条件 |

```

```
