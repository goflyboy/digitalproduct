## 一、总体数据模型（核心实体及关系）

### 1.1 建模边界与核心结论

电商产品（手机数码等）可以用 **Category -> SPU -> SKU** 三层模型覆盖，因为其核心问题是「选哪个颜色/容量组合」，SKU 是最终可售单元。

复杂产品（服务器、工业设备、PLC 配置器）不同。它的核心问题是：

- 产品由多级部件组成（CPU、内存、硬盘、电源、支架...）
- 每个部件分类下有多个候选 Part
- Part 之间存在数量、兼容、依赖、计算、优选等多种约束规则
- 同一产品平台可派生出多个可售型号（低端 S1110、高端 S22）
- 客户需要通过配置器选择组合，系统校验约束后输出 BOM/报价/交付规格

因此，复杂产品配置需要 **双层元模型 + 三层实例** 的结构：

| 层次 | 解决的问题 | 核心对象 | 典型责任人 |
| --- | --- | --- | --- |
| **L1 业务元模型** | 产品领域允许定义哪些业务类型及语义 | ProductClassType、PartClassType、ProductInstanceType、SpecDefinition、Parameter | IT 与公司级业务/行管人员 |
| **L2 业务对象实例** | 某产品平台的骨架是什么，可售型号如何裁剪 | ProductClass、PartClass、Part、ProductInstance | 产品数据架构师、产品数据工程师 |
| **L3 配置运行实例** | 客户本次选择什么，是否有效，输出什么 | Configuration、ConfiguredPart | 销售、客户、配置引擎 |

> **说明**：L0 平台基础元模型（OntoObjectType/OntoAttrType/OntoLinkType）由平台架构师负责定义，本文档聚焦业务层建模，暂不展开。

### 1.3 规格与参数的区别

这是本文模型的核心概念之一。动态属性（dynAttr）分为两类：**规格（Spec）** 和 **参数（Parameter）**，二者在语义、面向角色、可变性上有本质区别：

| 维度 | 规格（SpecDefinition） | 参数（Parameter） |
| --- | --- | --- |
| **语义** | 产品或部件本身已有的物理特性或性能指标 | 销售人员/客户可配置的需求输入 |
| **面向角色** | 研发、产品设计人员定义 | 一线产品经理、销售、客户使用和理解 |
| **是否可手工输入** | 否，继承 ProductClass 或 Part 的固定值 | 是，可由用户手工输入或修改 |
| **载体有无对应值** | ProductClass 有 SpecValue，Part 也有 SpecValue | Part 无 Parameter 值，参数值在配置阶段由用户输入 |
| **举例** | 服务器外形 2U（ProductClass）、CPU 核心数 2/4/8/18（Part）、硬盘容量 3TB（Part） | "5400rpm 硬盘总容量 >= 5TB"、"4核 CPU 总内存 >= 512GB" |
| **在模型中的位置** | 定义在 ProductClass 或 PartClass 上，挂在 ProductClass 或 Part 上都有值 | 定义在 ProductClass 或 PartClass 上，Part 无值 |
| **用途** | 定义产品或部件的固有能力边界 | 在配置阶段传递客户需求，驱动求解 |

**举例说明**：

- `FormFactor = 2U` 是产品类规格：服务器 SERVER_X86 的外形规格天生就是 2U，不可改
- `Capacity = 3` 是部件规格：Part sd1 的硬盘容量天生就是 3TB，不可改
- `Sum_Capacity >= 5` 是参数：客户说我需要至少 5TB 容量，这是需求输入，可以改

### 1.4 详细实体关系表

#### L1 业务元模型

| 实体名称 | 英文名 | 定义 | 关键字段 | 关联关系 |
|---------|--------|------|---------|---------|
| **产品类元模型** | ProductClassType | 产品族或产品平台类型，承载平台化和标准化 | code, name, domain, modeling_policy | composedOf → PartClassType |
| **部件类元模型** | PartClassType | 可配置子模块的抽象，如 CPU、硬盘、显示器 | code, name, part_kind, selection_policy, min/max_cardinality | hasSpec → SpecDefinition；hasParameter → Parameter；contains → PartClassType |
| **规格定义** | SpecDefinition | 产品的物理特性或性能指标定义 | code, name, data_type, unit, value_domain, required | definedOn → ProductClassType/PartClassType |
| **参数定义** | Parameter | 可由用户输入/修改的配置需求定义 | code, name, data_type, unit, min, max, default_value, assign_type | definedOn → ProductClassType/PartClassType |
| **可售产品元模型** | ProductInstanceType | 可售产品定义，如 S1110、S22 | code, name, market, status, effective_period | realizes → ProductClassType |

#### L2 业务对象实例

| 实体名称 | 英文名 | 定义 | 关键字段 | 关联关系 |
|---------|--------|------|---------|---------|
| **产品类** | ProductClass | 产品族或平台的可复用骨架（本身带版本，可发布多次） | id, code, name, version, status, effective_from/to | 1:N → PartClass；1:N → SpecValue |
| **部件分类** | PartClass | 可配置子模块的分类边界 | id, code, name, product_class_id, selection_policy, min_qty, max_qty, multi_instance | N:1 ← ProductClass；1:N → Part；1:N → SpecValue |
| **部件** | Part | PartClass 的具体实例，如一个明确编码的 CPU 或硬盘 | id, code, name, part_class_id, status, price | N:1 ← PartClass；1:N → SpecValue |
| **规格值** | SpecValue | 产品或部件的具体规格属性值，挂在 ProductClass 或 Part 上 | id, owner_type, owner_id, spec_code, value, unit | N:1 ← ProductClass / Part |
| **产品实例** | ProductInstance | 确定销售边界的可售产品（对标电商 SPU，本身带版本） | id, code, name, version, market, status, effective_from/to | realizes → ProductClass；N:M → Part（offersPart 边） |
| **规格覆盖** | SpecOverride | 产品实例相对于基线的规格差异 | id, product_instance_id, spec_code, override_value, reason | N:1 ← ProductInstance |

#### L3 配置运行实例

| 实体名称 | 英文名 | 定义 | 关键字段 | 关联关系 |
|---------|--------|------|---------|---------|
| **配置方案** | Configuration | 一次客户配置方案 | id, product_instance_id, model_snapshot_id, status, customer_context | N:1 ← ProductInstance |
| **已选部件** | ConfiguredPart | 已选 Part、实例号和数量 | configuration_id, part_id, instance_no, quantity, selected | N:1 ← Configuration, Part |
| **已选属性值** | ConfiguredValue | 本次用户输入的参数值 | owner_type/id, parameter_code, value, unit, source | N:1 ← Configuration |

## 二、详细数据案例（以服务器产品为例）

### 2.1 L1 业务元模型数据

#### 产品类元模型定义

| type_code | name | domain | modeling_policy | description |
|-----------|------|--------|-----------------|-------------|
| SERVER_X86 | X86服务器平台 | IT硬件 | PLATFORM_STANDARDIZATION | 面向研发和后端复用的通用服务器平台，承载平台化和标准化 |

#### 部件类元模型定义

| type_code | name | part_kind | selection_policy | min_cardinality | max_cardinality | multi_instance |
|-----------|------|-----------|------------------|-----------------|-----------------|----------------|
| cpu | CPU | COMPONENT | REQUIRED | 1 | 2 | false |
| drive | 硬盘 | STORAGE | OPTIONAL | 0 | 8 | true |
| memory | 内存 | COMPONENT | REQUIRED | 1 | 16 | true |
| software | 配套软件 | SERVICE | OPTIONAL | 0 | 10 | false |

#### 规格定义（SpecDefinition）

规格定义在产品类或部件类上，描述 ProductClass 或 Part 固有的物理特性或性能指标：

| spec_code | name | defined_on | data_type | unit | value_domain | required |
|-----------|------|-----------|-----------|------|--------------|----------|
| FormFactor | 外形规格 | SERVER_X86 | STRING | U | 1U,2U,4U | true |
| PowerSupply | 电源类型 | SERVER_X86 | STRING | - | SINGLE,DUAL | true |
| CoreNum | 核心数 | cpu | INTEGER | core | 2,4,8,18 | true |
| Memory | 内存容量 | cpu | INTEGER | GB | 123,256,512,1024 | true |
| ConfigType | 配置类型 | cpu | INTEGER | 配置 | 2,5 | true |
| Speed | 转速 | drive | STRING | rpm | 3000,5400,7200,9000 | true |
| Capacity | 容量 | drive | INTEGER | TB | 1,2,3,6,9 | true |
| Type | 类型 | drive | STRING | - | sd,md | true |

#### 参数定义（Parameter）

参数定义在部件类上，描述用户在配置时可输入的需求：

| param_code | name | defined_on | data_type | unit | assign_type | description |
|-----------|------|-----------|-----------|------|------------|-------------|
| Sum_Capacity | 硬盘总容量需求 | drive | INTEGER | TB | INPUT | 客户要求的硬盘总容量下限（可筛选转速） |
| Sum_Memory | CPU总内存需求 | cpu | INTEGER | GB | INPUT | 客户要求的某型号CPU总内存下限（可筛选核心数） |
| Quantity | 硬盘数量需求 | drive | INTEGER | 块 | INPUT | 客户要求的硬盘总数量 |

> **注意**：参数定义在部件类（PartClass）上，而不是具体的 Part。Part 本身没有参数值，参数值由用户在配置阶段输入。

## 四、新模型与 cruleengine 现有模型的关系

### 4.1 定位说明

新模型是 **数字产品全生命周期的业务事实模型**；cruleengine 主要是 **配置约束的声明和执行模型**。

二者是「业务事实源 → 可执行投影」关系：

```
数字产品模型（源）              cruleengine 执行模型（投影）
─────────────────              ───────────────────────────
ProductClass（含 version）──compile──> Module
PartClass              ──compile──> PartCategory
Part + SpecValue       ──compile──> Part + dynAttr
Parameter              ──compile──> Para
Configuration          <──result─── ModuleInst
ConfiguredPart         <──result──> PartInst / PartCategoryInst
```

### 4.2 概念映射表

| 新建模概念 | cruleengine 概念 | 关系和差异 |
| --- | --- | --- |
| ProductClass（含自带 version） | Module | Module 含版本、PartCategory、Part、Para，是执行投影；ProductClass 的 version 直接对应 Module 版本 |
| PartClass | PartCategory | 均表达候选分类；现有类已有 selectionPolicy、supportMultiInst 和递归结构 |
| Part | Part | 基本一致；业务层还需物料主数据、有效期、供应和销售状态 |
| SpecDefinition | DynamicAttribute | 均支持类型和选项；业务层还需单位、值域、治理和版本 |
| SpecValue | dynAttr value | ProductClass 或 Part 的规格值对应引擎中的属性值 |
| Parameter | Para | 对应输入、计算和汇总参数（用户可变的配置需求） |
| ProductInstance（含自带 version） | 裁剪后的 Module 实例 | 通过 offersPart 边裁剪部件候选集，ProductInstance 自身 version 不再引入 ProductInstanceVersion |
| ConfigurationSolution | ModuleInst | ModuleInst 承载数量、优先级值和分类实例 |
| ConfiguredPart | PartInst | 对应 quantity、selected、hidden 和选中属性 |
| offersPart 边 | 裁剪后的候选集 | 通过 enabled/disabled 边表达，与引擎的 PartCategoryInst 关联 |

### 4.3 MultiPCTest 样例映射

基于 `MultiPCTest.java` 中的 `MultiPCConstraint` 类：

| 新建模 | cruleengine | 示例 |
| --- | --- | --- |
| PartClass: drive | PartCategoryVar drive | 硬盘部件分类 |
| PartClass: cpu | PartCategoryVar cpu | CPU部件分类 |
| SpecDefinition: Speed | @DAttrAnno(code = "Speed", ...) | 转速属性 |
| SpecDefinition: Capacity | @DAttrAnno(code = "Capacity", ...) | 容量属性 |
| SpecDefinition: CoreNum | @DAttrAnno(code = "CoreNum", ...) | 核心数属性 |
| SpecDefinition: Memory | @DAttrAnno(code = "Memory", ...) | 内存容量属性 |
| Parameter: Sum_Capacity | ParaVar Sum_Capacity | 硬盘总容量需求参数 |
| Parameter: Sum_Memory | ParaVar Sum_Memory | CPU总内存需求参数 |
| Part: sd1, sd2, sd3 | @PartAnno(fatherCode = "drive", ...) | 固态硬盘实例 |
| Part: md1, md2, md3 | @PartAnno(fatherCode = "drive", ...) | 机械硬盘实例 |
| Part: cpu1, cpu2, cpu3, cpu4 | @PartAnno(fatherCode = "cpu", ...) | CPU实例 |
| ConfigurationSolution | inferRecommendModule() | 配置求解入口 |
| ConfiguredPart | ModuleInst 输出 | 包含 Q(quantity), H(hidden), S(selected) |

### 4.4 需要保持的边界

1. **Module 不应兼任产品主数据仓库**。应由编译或适配层从已发布 ProductClass 业务模型生成 Module。ProductClass 自带 version 字段，不要再加 ProductClassVersion。

2. **现有 Part.price 只是单值**，不足以承载币种、区域、渠道、阶梯和有效期定价。业务模型应引用独立定价域。

3. **Spec 和 Parameter 的区别要保持**：
   - SpecDefinition 既可定义在 ProductClass 上也可定义在 PartClass 上，ProductClass 和 Part 都有自己的 SpecValue，描述产品或部件固有属性
   - Parameter 定义在 ProductClass 或 PartClass 上，对应的 Part 无 Parameter 值，描述用户可变的配置需求

4. **ProductInstance 可编译成裁剪后的 Module**，也可使用基础 Module 加候选集过滤输入。ProductInstance 自带 version，不要再加 ProductInstanceVersion。

5. **模型升级需要快照机制**。历史报价和 BOM 必须能够复现，不能因为模型变更导致历史配置无法验证。

## 五、备选方案：Part 规格值的两种图建模方式（属性 vs. 边）

> **章节定位**：前文 §1.4 / §2.1 / §2.2 已采用「Part 自身属性 = SpecValue」的标准建模。本章作为**备选方案**专门论证：当业务方倾向"SKU 不继承 SPU、属性全部实例化（扁平化）"的场景下，把 SpecValue 当成 Part 的**属性**还是当成 Part → AttributeValue 节点的**边**，各自的得失。

### 5.1 问题来源：电商 SKU 扁平化场景

电商 SPU/SKU 在很多业务中是这样建模的：

```
SPU iPhone 16 ──┬── SKU: iPhone16 256G 黑色   (颜色=黑色, 容量=256GB, 制式=公开版, ...)
                ├── SKU: iPhone16 512G 钛色    (颜色=钛色, 容量=512GB, 制式=公开版, ...)
                └── SKU: iPhone16 128G 黑色电信 (颜色=黑色, 容量=128GB, 制式=电信版, ...)
```

关键差异：

| 维度 | 复杂产品（本文主线） | 电商 SKU 扁平化 |
|------|-------------------|---------------|
| 属性的"层级" | Part 继承 PartClass 的 SpecDefinition | SKU 直接持有全部属性值，没有"模板层" |
| 属性共享 | 同 PartClass 的 Part 共用同一组 SpecDefinition | 不同 SKU 之间属性可任意组合 |
| 属性数量 | PartClass 通常 3~10 个规格 | SKU 可达 20~50 个属性 |
| 查询主场景 | 「满足 4 核 CPU 且内存 ≥ 512GB 的 Part」 | 「重量=10 的 SKU」「重量≥100 的 SKU」|

最后一行是本章要回答的核心问题：**当业务主场景是「属性过滤」（重量 = 10 或 ≥ 100）时，把属性建模成节点的属性 还是 节点之间的边，性能/能力差异如何？**

### 5.2 方案 A：SpecValue 作为 Part 节点自身的属性

#### 5.2.1 数据形态

```cypher
// Neo4j Cypher 表示
(:Part {code:'cpu1', CoreNum:2, Memory:123, ConfigType:2})
(:Part {code:'cpu2', CoreNum:4, Memory:256, ConfigType:2})
(:Part {code:'sd1',  Speed:5400, Capacity:3, Type:'sd'})
```

```sparql
# Stardog SPARQL 表示
:cpu1 :CoreNum 2 ; :Memory 123 ; :ConfigType 2 .
:sd1  :Speed 5400 ; :Capacity 3 ; :Type "sd" .
```

#### 5.2.2 优点

1. **属性过滤是最快路径**：原生属性索引（Neo4j 的 schema index / Stardog 的 predicate index）直接命中，不需要再走边的 join
2. **范围查询高效**：`WHERE p.Memory >= 512` 走 B-tree / range index，单表 O(log N)
3. **存储紧凑**：每 Part 一个节点 + K 个属性，节点数和边数最少
4. **写入简单**：批量更新 SpecValue 就是 `SET n.Memory = 256`
5. **JSON / CSV 导出自然**：与业务系统的"扁平表"心智模型一致
6. **图遍历 + 过滤混合场景强**：先沿关系拿到候选 Part 集，再 `WHERE p.Weight >= 100`，一步到位

#### 5.2.3 缺点

1. **属性 schema 不固定**：不同 PartClass 的 Part 节点上的属性集合不同（cpu 有 CoreNum，drive 有 Speed），节点是"异构 schema"
2. **不支持二级索引**：无法在 (PartClass, 属性名, 值) 上做"以属性名查值"反向查询（用起来少）
3. **多值属性难**：如果一个属性有多个值（如 Part 的"接口类型"集合），只能序列化为字符串数组，失去属性索引能力
4. **属性变化代价高**：新增属性（如要给所有 drive 加 NoiseLevel）需遍历所有 Part 节点
5. **无法表达"值本身"的语义**：50 这个数字，可以是 GB 也可以是 TB，节点属性不会区分
6. **跨引擎迁移成本**：Cypher / GQL / SPARQL 之间的属性访问语法差异较大

#### 5.2.4 配置查询场景的性能特点

```sql
-- 主场景：重量等于 10 / 大于等于 100
WHERE p.Weight = 10       -- 等值过滤：O(log N) 索引命中
WHERE p.Weight >= 100     -- 范围过滤：O(log N) range index 命中
```

实测参考（Neo4j 4.x/5.x + Property Index，1M Part 节点，单属性过滤）：

| 查询 | 索引命中 | 延迟 |
|------|---------|------|
| `MATCH (p:Part) WHERE p.Weight = 10` | 单值 B-tree | < 5 ms |
| `MATCH (p:Part) WHERE p.Weight >= 100` | range scan | 5~20 ms |
| `MATCH (p:Part) WHERE p.Weight BETWEEN 50 AND 150` | range scan | 10~30 ms |
| 跨 2 个属性 `Weight >= 100 AND Capacity >= 3` | composite index 更优 | 10~40 ms |

### 5.3 方案 B：SpecValue 作为 Part → AttributeValue 节点的一条边

#### 5.3.1 数据形态

```cypher
(:Part {code:'cpu1'})
    -[:HAS_SPEC {spec:'CoreNum',   unit:'core'}]->(:AttributeValue {value:2})
    -[:HAS_SPEC {spec:'Memory',    unit:'GB'}]->(:AttributeValue {value:123})
    -[:HAS_SPEC {spec:'ConfigType',unit:'-'}]->(:AttributeValue {value:2})

(:Attribute {code:'CoreNum', dataType:'INTEGER', unit:'core'})
(:Attribute {code:'Weight',  dataType:'DECIMAL', unit:'kg'})
```

```sparql
:cpu1 :hasSpec :sv_cpu1_core .   :sv_cpu1_core :spec "CoreNum" ; :value 2 .
```

#### 5.3.2 优点

1. **属性 schema 稳定**：`Part` 节点没有属性，只有统一 `(p)-[:HAS_SPEC]->(av)-[:OF_ATTR]->(attr)` 三元结构
2. **多值属性自然**：一个 Part 可以对同一 Spec 出多条边（例：接口类型 = [USB, HDMI]）
3. **值的元数据可挂**：`(AttributeValue)-[:OF_ATTR]->(Attribute)` 上挂 unit / dataType / valueDomain，能反向校验
4. **跨类型统一查询**：「所有 SpecValue 中值=10 的对象」用一条 MATCH 即可跨 Part / ProductClass / SKU 等任意实体
5. **属性的版本/历史可挂**：在 `:HAS_SPEC` 边上挂 effectiveFrom / source，便于做"按时间过滤"
6. **W3C 标准原生**：RDF/OWL 模型本来就是"实体-属性-值"三元，Stardog 上 SHACL 校验天然支持

#### 5.3.3 缺点

1. **属性过滤性能差**：`MATCH (p:Part)-[:HAS_SPEC]->(av {value:10})` 是图遍历，**不是**索引命中，需要做 (属性名, 值) 复合索引才能接近属性查询
2. **范围查询更慢**：要走边 + 节点属性扫描，除非在 `(HAS_SPEC.spec, av.value)` 上建复合索引
3. **存储翻倍**：每 SpecValue 多 1 节点 + 1 边，Part × SpecCount 的图规模
4. **跨属性过滤代码复杂**：「`Weight >= 100 AND Capacity >= 3`」要写两条 MATCH，性能是两次图遍历的叠加
5. **关系代数开销**：边遍历在 OLTP 查询中比属性访问慢 5~20 倍（经验值，依引擎而定）

#### 5.3.4 配置查询场景的性能特点

```cypher
-- 主场景：重量等于 10 / 大于等于 100
MATCH (p:Part)-[:HAS_SPEC]->(av:AttributeValue)
WHERE av.spec = 'Weight' AND av.value = 10
-- 性能：取决于是否在 (spec, value) 上建索引。无索引：O(N)；有索引：O(log N)

MATCH (p:Part)-[:HAS_SPEC]->(av:AttributeValue)
WHERE av.spec = 'Weight' AND av.value >= 100
-- 范围扫描在属性图上需要显式建 composite index；纯边遍历无法用 range scan
```

### 5.4 方案对比总表

| 维度 | 方案 A：属性 | 方案 B：边+节点 | 谁优 |
|------|-------------|----------------|------|
| **等值过滤** `Weight = 10` | 单值 B-tree 索引，O(log N) | 需复合索引 (spec, value) | A |
| **范围过滤** `Weight >= 100` | range scan，原生支持 | 需 composite index + range scan | A |
| **多属性过滤** `Weight >= 100 AND Capacity >= 3` | 两列 index + intersect | 两次 MATCH + 节点交集 | A |
| **跨类型统一查询**「所有值=10 的实体」 | 每种类型各写一次 | 一条 MATCH 即可 | B |
| **多值属性** | 序列化为数组，丧失索引 | 多个 `:HAS_SPEC` 边 | B |
| **属性 schema 演进** | 异构 schema，迁移难 | 节点结构稳定 | B |
| **值的元数据**（unit/dataType） | 不易挂载 | 天然可挂 | B |
| **W3C / SHACL 校验** | 需要额外表达 | RDF/OWL 原生 | B |
| **存储** | 紧凑 | 节点/边翻倍 | A |
| **写入** | 单次 `SET` | 多次 `CREATE` | A |
| **跨引擎迁移** | Cypher/GQL/SPARQL 差异 | 较一致 | B |

### 5.5 对图数据库的能力要求

#### 方案 A 要求

| 能力 | 说明 | 必要性 |
|------|------|------|
| **节点属性索引**（property index / schema index） | 单值等值过滤必须 | 必需 |
| **复合索引**（composite / multi-column index） | 多属性过滤必须 | 必需 |
| **范围索引**（range index） | `>=`、`<=`、`BETWEEN` 必须 | 必需 |
| **异构节点 schema 容忍** | 同一 Label 下节点属性可不同 | 必需 |
| **数据类型校验** | INTEGER/DECIMAL/STRING 等类型 | 推荐 |
| **JSON 序列化** | 部分异构属性序列化输出 | 可选 |

适用引擎：

| 引擎 | 方案 A 适配度 | 说明 |
|------|------------|------|
| **Neo4j Aura** | ⭐⭐⭐⭐⭐ | Property Index + Composite Index + Range Index 原生一等公民 |
| **Microsoft Fabric IQ** | ⭐⭐⭐⭐ | Graph item 是 LPG，等值/范围都支持，但复合索引能力弱于 Neo4j |
| **Stardog** | ⭐⭐⭐⭐ | 属性可建 predicate index + range；OWL DataProperty 表达规整 |
| **AbutionGraph** | ⭐⭐⭐⭐ | Edge + 属性索引，T/P/F 模型原生 |
| **TDengine IDMP** | ⭐⭐⭐ | Element + Attribute 三件套可表达，但本质是工业时序 |

#### 方案 B 要求

| 能力 | 说明 | 必要性 |
|------|------|------|
| **节点 + 边遍历** | 图遍历基本能力 | 必需 |
| **复合索引 `(属性名, 值)`** | `(:HAS_SPEC {spec:'Weight'})-[]->(:AttributeValue {value:10})` 等值过滤 | 必需（否则慢到不可用） |
| **范围索引 `(属性名, 值范围)`** | `value >= 100` 走 range scan | 必需 |
| **多跳关系遍历** | 反向查询（值 → Spec → Part）需要 | 推荐 |
| **SHACL / OWL 校验** | 值域、单位、required 等 | 推荐 |
| **时序 / 历史** | SpecValue 在不同时间的值 | 可选 |

适用引擎：

| 引擎 | 方案 B 适配度 | 说明 |
|------|------------|------|
| **Stardog** | ⭐⭐⭐⭐⭐ | RDF/OWL 一等公民，predicate + reification 表达边属性，SHACL 校验原生 |
| **Microsoft Fabric IQ** | ⭐⭐⭐⭐ | Relationship Type + Mapping Table，但复合索引需要应用层配合 |
| **Neo4j Aura** | ⭐⭐⭐⭐ | 原生支持，但 `:HAS_SPEC` 边的 composite index 需要显式建 |
| **AbutionGraph** | ⭐⭐⭐⭐⭐ | Edge 原生带属性 + 边聚合独占能力 |
| **TDengine IDMP** | ⭐⭐ | Element Reference 跨树引用表达，但范围查询弱 |

### 5.6 在我们配置查询主场景下的最终选择

#### 5.6.1 主场景特征

我们的核心主场景是：

```sql
-- 主场景 1：等值过滤
MATCH (p:Part) WHERE p.Weight = 10

-- 主场景 2：范围过滤
MATCH (p:Part) WHERE p.Weight >= 100

-- 主场景 3：多属性组合过滤（产品配置器的实际场景）
MATCH (p:Part)
WHERE p.CoreNum = 4 AND p.Memory >= 512

-- 主场景 4：沿关系 + 属性过滤（客户配置 S1110 时的候选过滤）
MATCH (pi:ProductInstance {code:'S1110'})-[:OFFERS_PART]->(p:Part)
WHERE p.Capacity >= 5 AND p.Type = 'sd'
```

这些场景中，**所有过滤都是属性过滤**，且都需要：

1. 单属性等值
2. 单属性范围
3. 多属性 AND
4. 沿关系拿候选集 + 属性过滤

#### 5.6.2 结论：方案 A 显著占优，但需要"边 + 节点"的混合补救

**主路径（90% 的配置查询）：采用方案 A**

- 范围/等值/复合过滤全部走索引，性能是方案 B 的 5~20 倍
- 与现有关系型业务库心智一致
- 与 cruleengine 的 `@DAttrAnno` 注解模型直接对位

**补救路径（10% 的复杂语义场景）：方案 B 的子集**

只在以下场景引入 `(Part)-[:HAS_SPEC]->(AttributeValue)` 边：

1. **多值属性**（如 Part 的接口集合 [USB, HDMI]）—— 序列化为数组后无法做单值过滤，必须用边
2. **值的元数据**（如单位 / 数据类型 / 校验规则要挂在值上）—— 属性方案只能挂在 Part 上，结构冗余
3. **值的版本/历史**（如 SpecValue 在不同 effectivePeriod 的值）—— 属性方案只能"覆盖写"，无法保留历史
4. **跨类型统一查询**（如"找所有值=10 的实体，包括 Part、ProductClass、SKU"）—— 属性方案需要按类型各写一次

**混合方案示意**：

```
Part (方案A 主路径)
├── 属性层 (node properties, 走索引)
│     ├── CoreNum: 4
│     ├── Memory: 256
│     ├── Capacity: 3
│     ├── Type: 'sd'
│     └── Weight: 10
│
└── 边层 (方案B 补救，仅在需要时)
      ├── -[:HAS_MULTIVALUED_ATTR]->(:MultiValuedAttrSet)   -- 接口集合等
      ├── -[:HAS_SPEC_WITH_META]->(:AttributeValue)-[:OF_ATTR]->(:Attribute)  -- 带元数据
      └── -[:HAS_SPEC_HISTORY]->(:AttributeValueHistory)   -- 历史值
```

#### 5.6.3 决策矩阵

| 你的核心主场景 | 建议 | 备注 |
|---------------|------|------|
| **主要是范围/等值过滤**（重量 ≥ 100） | **方案 A** | 索引覆盖，性能最高 |
| **主要是多值 / 元数据 / 历史** | **方案 B** 或 **混合方案** | 单值过滤慢 5~20 倍是代价 |
| **跨类型统一查询**（"所有值=10 的对象"） | **方案 B** 或 **混合方案** | 单一 MATCH 跨多类型 |
| **配置求解 + 沿关系过滤**（S1110 候选 + 重量过滤） | **方案 A** | 沿 OFFERS_PART 边拿到候选后，在属性层一步过滤 |
| **多 W3C 形式化校验** | **方案 B** | SHACL 在 RDF 上原生 |
| **两种都不可少** | **混合方案** | 90% 主路径走 A，10% 复杂场景走 B |

### 5.7 与现有方案的衔接

- §1.4 / §2.2 中的 `SpecValue` 表是**方案 A 的关系型落地**，与方案 A 的图建模一致：SpecValue 是挂在 Part / ProductClass 上的属性（或独立行承载）。
- §4.2 概念映射表中的 `SpecValue → dynAttr value` 也是方案 A 的体现：dynAttr value 是 Part 上的属性，不是独立节点。
- **如果引入方案 B 的部分元素**，需要补充：`Attribute`（规格元数据节点）、`AttributeValue`（规格值节点）、`(:Part)-[:HAS_SPEC]->(:AttributeValue)` 边。建议仅在电商 SKU 扁平化场景下引入。

## 七、附录

### 7.1 术语表

| 术语 | 全称 | 说明 |
|------|------|------|
| SpecDefinition | 规格定义 | 产品的物理特性或性能指标定义，Part 有对应 SpecValue |
| SpecValue | 规格值 | Part 的具体规格属性值 |
| Parameter | 参数 | 可由用户输入/修改的配置需求定义，Part 无对应 Parameter 值 |
| ProductClass | 产品类 | 产品族或平台的可复用骨架，承载平台化和标准化 |
| PartClass | 部件分类 | 可配置子模块的分类边界，如 CPU、硬盘 |
| Part | 部件 | PartClass 的具体实例，如 cpu1、sd1 |
| ProductInstance | 产品实例 | 确定销售边界的可售产品，对标电商 SPU |
| offersPart 边 | 部件裁剪边 | ProductInstance 到 Part 的关系边，携带 enabled/default/minQty/maxQty/fixed |
| Configuration | 配置方案 | 一次客户配置方案 |
| ConfiguredPart | 已选部件 | 配置方案中被选中的部件及其数量 |
| ConfiguredValue | 已选参数值 | 配置阶段用户输入的参数值 |

### 7.2 规格 vs 参数速查

| 问题 | 答案 |
|------|------|
| 服务器外形（2U/4U）是规格还是参数？ | 产品类规格，因为外形是 ProductClass SERVER_X86 固有的物理属性 |
| 硬盘容量是规格还是参数？ | 部件规格，因为容量是 Part sd1 固有的（3TB） |
| 客户需要"至少 5TB 容量"是什么？ | 参数，因为这是用户可配置的输入需求 |
| CPU 核心数是规格还是参数？ | 部件规格，因为核心数是 CPU 固有的（2/4/8/18） |
| 客户要求"4 核 CPU 总内存 >= 512GB"是什么？ | 参数，因为这是用户可配置的筛选条件 |
| Parameter 有 SpecValue 吗？ | 没有，Parameter 值在 Configuration 中由用户输入 |
| SpecValue 只挂在 Part 上吗？ | 不，ProductClass 也可以挂自己的 SpecValue（产品层规格） |

### 7.3 数据流向总结

```
产品数据架构师
     ↓
创建 ProductClass（自帶 version） + PartClass → 定义 SpecDefinition → 定义 Parameter
     ↓
录入 Part + SpecValue → 录入 ProductClass 自身的 SpecValue → 发布 ProductClass = SERVER_X86
     ↓
产品数据工程师
     ↓
创建 ProductInstance (S1110@1.0.0 / S22@1.0.0，ProductInstance 自帶 version)
     ↓
通过 offersPart 边裁剪部件候选集 → 发布产品实例
     ↓
销售/客户
     ↓
选择 ProductInstance → 输入 Parameter 值 → 配置引擎求解
     ↓
输出 ConfiguredPart + BOM/报价/交付规格
```
