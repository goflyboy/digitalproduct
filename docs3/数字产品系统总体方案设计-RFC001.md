## 一、背景与目标

### 1.1 项目背景

数字产品系统是复杂产品配置系统的泛化，旨在构建 AI 时代下面向 Agent 高度可消费的数据载体。与复杂产品配置模型相比，数字产品引入了两个核心维度：

| 维度 | 说明 | 示例 |
|---|---|---|
| **多维性** | 每层信息支持多维度扩展 | SPEC/MARKETING/DELIVERY/FINANCE/OPERATION |
| **多层性** | Module 递归嵌套，支持图的引用遍历 | CONTAINS/EXTENDS/REFERENCES 边类型 |

### 1.2 核心目标

| 目标 | 说明 |
|---|---|
| **前台（数字产品前台）** | 面向业务人员的产品建模与实例化操作界面 |
| **后台（数字产品服务层）** | 元数据管理 + 产品模型管理 + 产品实例化 + 产品数据服务 |
| **LinkX 图平台** | 底层图数据库，负责实例数据存储与图的多跳查询 |

### 1.3 设计原则

1. **语义与存储分离**：数字产品服务层管理元数据和业务语义；LinkX 负责图实例数据的存储和查询
2. **维护态数据全量入图**：所有维护态业务数据存储在 LinkX 图数据库中
3. **过程态数据备选方案**：复杂计算结果可选择入图或本地缓存
4. **增量同步**：支持 LinkX 故障时的数据补偿

## 二、模块所有权

### 2.1 服务模块划分

| 模块 | 职责 | 说明 |
|---|---|---|
| **元数据管理服务** | OntoObjectType、OntoAttrType、OntoLinkType、OntoInterfaceType | LinkX Schema 语义扩展 |
| **产品模型管理服务** | Module、Part、BusinessObject、ModuleLink、ModuleObjectRelation | 核心业务实体管理 |
| **产品实例化服务** | ModuleInstance、Part裁剪、规格覆盖、发布管理 | 销售产品实例化 |
| **产品数据服务** | 图查询、多维投影、领域概念接口 | 对外提供数据消费接口 |
| **发布管理服务** | VersionService、StateMachine、PublishValidator | DRAFT→PUBLISHED 状态流转 |
| **LinkX Sync 服务** | LinkXClient、SchemaSync、InstanceSync、CompensateSync | 调用现有 LinkX 服务同步数据 |

### 2.2 模块边界约束

```
数字产品服务层
    │
    ├── 元数据管理服务
    │       └── 不依赖 LinkX（纯语义定义）
    │
    ├── 产品模型管理服务
    │       ├── 依赖元数据管理服务
    │       └── 依赖 LinkX Sync 服务
    │
    ├── 产品实例化服务
    │       ├── 依赖产品模型管理服务
    │       └── 依赖发布管理服务
    │
    ├── 产品数据服务
    │       ├── 依赖产品模型管理服务
    │       └── 委托 LinkX 进行图查询
    │
    ├── 发布管理服务
    │       └── 依赖 LinkX Sync 服务
    │
    └── LinkX Sync 服务
            └── 调用外部 LinkX 图平台
```

### 5.2 LinkX 数据存储策略

#### 5.2.1 存储策略总览

| 数据类型 | 存储位置 | 说明 |
|---|---|---|
| **维护态数据** | LinkX 图数据库 | 所有业务实体（Module/Part/BusinessObject 等）全量存储在 LinkX |
| **过程态数据** | 备选方案 | 复杂计算结果可选择入图或本地缓存 |

#### 5.2.2 LinkX 节点类型映射

| 业务实体 | LinkX 节点类型 | 属性 |
|---|---|---|
| Module (PRODUCT) | `DIGITAL_PRODUCT` | code, name, version, status, module_type, depth, effective_from/to |
| Module (COMPONENT) | `COMPONENT_MODULE` | code, name, version, status, depth, effective_from/to |
| Module (PART) | `VIRTUAL_PART` | code, name, version, status |
| Part | `PART_INSTANCE` | code, name, status, price, price_unit |
| BusinessObject | `BUSINESS_OBJECT` | code, name, object_type, description, schema |
| BusinessObjectInstance | `BO_INSTANCE` | business_object_id, owner_type, owner_id, values, effective_from/to |
| ModuleObjectRelation | `MODULE_BO_RELATION` | module_id, business_object_id, relation_type, dimension, cardinality |
| ModuleInstance | `PRODUCT_INSTANCE` | code, name, version, status, module_id, enabled_parts, disabled_parts |

#### 5.2.3 LinkX 边类型映射

| 业务关系 | LinkX 边类型 | 属性 |
|---|---|---|
| ModuleLink.CONTAINS | `CONTAINS` | min_cardinality, max_cardinality, selection_policy |
| ModuleLink.EXTENDS | `EXTENDS` | - |
| ModuleLink.REFERENCES | `REFERENCES` | - |
| Part → Module | `BELONGS_TO` | - |
| BusinessObjectInstance → BusinessObject | `INSTANCES` | - |
| ModuleObjectRelation | `HAS_BUSINESS_OBJECT` | relation_type, dimension, inheritance_policy |

#### 5.2.4 过程态数据备选方案

**场景**：复杂计算结果（如 BOM 展开、配置求解结果）

| 方案 | 优点 | 缺点 | 适用场景 |
|---|---|---|---|
| **A. 入 LinkX 图** | 图查询能力复用、跨系统共享 | 增加 LinkX 存储压力 | 需跨系统共享的结果 |
| **B. 本地缓存** | 性能高、实现简单 | 需管理缓存一致性 | 仅本系统使用的中间结果 |
| **C. 不持久化** | 节省存储 | 每次重算 | 无状态计算 |

**决策**：默认方案 B（本地缓存），仅当需要跨系统共享时使用方案 A（入 LinkX）。

   - 调用 LinkXDB 的 createNodeType 接口，创建节点类型
   - 调用 LinkXDB 的 createEdgeType 接口，创建边类型
   - 返回 Schema 创建结果

#### 6.1.6 产品模型发布

**参与者**：产品数据架构师、VersionService、LinkXSync、DP数据库、LinkXDB

**操作过程描述**：

   - 产品数据架构师点击"发布"按钮
   - 调用 VersionService.publishModule()

2. **校验完整性**
   - VersionService 校验模块完整性：
     - 检查是否设置了必要的 BusinessObject
     - 检查 ModuleLink 关系是否完整

   - 校验通过后，更新 Module.status = PUBLISHED
   - 记录发布人和发布时间

4. **同步 LinkX**
   - LinkXSync 更新 LinkXDB 中节点状态
   - 确保所有节点状态为 ACTIVE

### 6.4 数据发布与版本管理方案

#### 6.4.1 方案 A：版本管理在当前图中控制

**核心思想**：在同一张 LinkX 图中，通过节点属性（如 `version`、`effective_from`、`effective_to`）区分不同版本，所有版本共存。

**实现方式**：

| 版本类型 | 节点属性 | 说明 |
|---|---|---|
| 工作版本 | `status = DRAFT` | 当前正在编辑的草稿 |
| 已发布版本 | `status = PUBLISHED`, `effective_from ≤ now ≤ effective_to` | 当前生效的正式版本 |
| 历史版本 | `status = PUBLISHED`, `effective_to < now` | 已过期的历史版本 |
| 未来版本 | `status = PUBLISHED`, `effective_from > now` | 预定的未来版本 |

**LinkX 节点示例**：

```
# Module 节点（同一 code 有多个版本共存）
Node(DIGITAL_PRODUCT) {
  code: "NETWORK_PLATFORM",
  version: "1.0.0",
  status: "PUBLISHED",
  effective_from: "2026-01-01",
  effective_to: "2026-12-31"
}

Node(DIGITAL_PRODUCT) {
  code: "NETWORK_PLATFORM",
  version: "2.0.0",
  status: "PUBLISHED",
  effective_from: "2027-01-01",
  effective_to: null
}

Node(DIGITAL_PRODUCT) {
  code: "NETWORK_PLATFORM",
  version: "2.0.0-draft",
  status: "DRAFT",
  effective_from: null,
  effective_to: null
}
```

**版本查询策略**：

```java
// 查询当前生效版本
TraverseRequest request = TraverseRequest.builder()
    .nodeType("DIGITAL_PRODUCT")
    .filters(Map.of(
        "code", "NETWORK_PLATFORM",
        "status", "PUBLISHED",
        "effective_from", "<=2026-07-29",
        "effective_to", ">=2026-07-29"
    ))
    .build();

// 查询最新版本
TraverseRequest latestRequest = TraverseRequest.builder()
    .nodeType("DIGITAL_PRODUCT")
    .filters(Map.of(
        "code", "NETWORK_PLATFORM",
        "status", "PUBLISHED"
    ))
    .orderBy("version DESC")
    .limit(1)
    .build();
```

**优点**：
- 架构简单，无需维护多张图
- 历史版本查询方便，支持版本回溯
- 图遍历时可选择特定版本

**缺点**：
- 图数据量随版本增加而增长
- 跨版本查询需过滤条件
- 版本切换时需更新 effective_to

---

#### 6.4.2 方案 B：版本管理在独立发布库的图中控制

**核心思想**：维护两张独立的图——工作图（Draft Graph）和发布图（Published Graph）。工作图保存草稿状态，发布图保存已发布版本的快照。

**实现方式**：

| 图类型 | 用途 | 内容 |
|---|---|---|
| **Draft Graph** | 工作图 | 所有 DRAFT 状态的节点，实时更新 |
| **Published Graph** | 发布图 | 每次发布时的工作图快照，**不可修改** |

**发布流程**：

```
┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
│   Draft Graph   │ ──▶ │ VersionService   │ ──▶ │ Published Graph  │
│   (工作图)      │     │ (发布服务)      │     │   (发布图)      │
│                 │     │                 │     │                 │
│ DRAFT 版本      │     │ 发布时执行：     │     │ PUBLISHED 快照  │
│ 实时编辑        │     │ 1. 校验完整性    │     │ 不可修改        │
│                 │     │ 2. 深度拷贝      │     │ 保留历史版本    │
│                 │     │ 3. 创建快照      │     │                 │
└─────────────────┘     └─────────────────┘     └─────────────────┘
                              │
                              │ 发布后
                              ▼
                        ┌─────────────────┐
                        │   Draft Graph   │
                        │   (工作图)       │
                        │                 │
                        │ 复制发布版本     │
                        │ 作为新草稿       │
                        │ 继续编辑        │
                        └─────────────────┘
```

**版本查询策略**：

```java
// 查询已发布版本列表
List<String> publishedVersions = linkXClient.queryNodes(NodeQuery.builder()
    .nodeType("DIGITAL_PRODUCT")
    .graphName("published")
    .filters(Map.of("code", "NETWORK_PLATFORM"))
    .orderBy("version DESC")
    .build());

// 查询特定发布版本
Node publishedNode = linkXClient.getNodeById(NodeId.builder()
    .graphName("published")
    .nodeType("DIGITAL_PRODUCT")
    .code("NETWORK_PLATFORM")
    .version("1.0.0")
    .build());

// 查询工作版本
Node draftNode = linkXClient.getNodeById(NodeId.builder()
    .graphName("draft")
    .nodeType("DIGITAL_PRODUCT")
    .code("NETWORK_PLATFORM")
    .build());
```

**LinkX 图结构示例**：

```
# Draft Graph（工作图）
Graph(draft) {
  Node(DIGITAL_PRODUCT) {
    code: "NETWORK_PLATFORM",
    version: "2.0.0-draft",
    status: "DRAFT"
  }
}

# Published Graph（发布图，按版本隔离）
Graph(published@1.0.0) {
  Node(DIGITAL_PRODUCT) {
    code: "NETWORK_PLATFORM",
    version: "1.0.0",
    status: "PUBLISHED"
  }
}

Graph(published@1.1.0) {
  Node(DIGITAL_PRODUCT) {
    code: "NETWORK_PLATFORM",
    version: "1.1.0",
    status: "PUBLISHED"
  }
}
```

**优点**：
- 发布图完全不可变，数据安全性高
- 历史版本隔离，支持精确回溯
- 适合合规审计场景

**缺点**：
- 需要维护多张图，运维复杂度增加
- 版本间共享数据（如共享的 Part）需特殊处理
- 图存储成本增加

---

#### 6.4.3 方案对比与推荐

| 评估维度 | 方案 A（单图多版本） | 方案 B（多图隔离） |
|---|---|---|
| **架构复杂度** | ⭐⭐ 简单 | ⭐⭐⭐⭐ 复杂 |
| **存储成本** | ⭐⭐ 较低（增量存储） | ⭐⭐⭐⭐ 较高（全量快照） |
| **版本隔离性** | ⭐⭐⭐ 一般（属性过滤） | ⭐⭐⭐⭐⭐ 完全隔离 |
| **历史追溯** | ⭐⭐⭐⭐ 方便 | ⭐⭐⭐⭐⭐ 非常方便 |
| **回滚能力** | ⭐⭐⭐ 通过更新 effective_to | ⭐⭐⭐⭐⭐ 直接切换图 |
| **运维复杂度** | ⭐⭐ 简单 | ⭐⭐⭐⭐ 复杂 |
| **适用场景** | 快速迭代、内部系统 | 金融、医疗、合规要求高 |

**推荐**：对于数字产品系统，建议采用**方案 A（单图多版本）**，原因如下：
1. 数字产品变更频率相对较低，不需要完全隔离
2. 架构简单，运维成本低
3. 支持通过 effective_from/to 实现版本时效控制
4. 如有合规需求，可在方案 A 基础上增加归档机制

### 6.5 阶段三：数据消费（图查询）

#### 6.5.1 图的多跳查询（通过产品数据服务）

**参与者**：业务系统/前端、DataQueryService、LinkXSync、DP数据库、LinkXDB

**操作过程描述**：

1. **发起图查询请求**
   - 业务系统传入起始节点 ID（如 CORE_SWITCH）
   - 指定查询类型（REFERENCES）和最大深度（5）

2. **解析查询请求**
   - DataQueryService 解析查询参数
   - 构建 LinkX 图遍历请求

3. **执行图遍历**
   - LinkXSync 将请求转发给 LinkXDB
   - LinkXDB 执行多跳遍历
   - 返回遍历结果（包含路径和节点信息）

4. **聚合结果**
   - DataQueryService 聚合遍历结果
   - 构建响应 DTO 返回给调用方

**数据变更**：无（仅查询）

## 十、关键技术决策

### 10.1 数据存储策略

**决策**：维护态数据全量入 LinkX，过程态数据备选方案

| 数据类型 | 存储位置 | 说明 |
|---|---|---|
| 维护态数据 | LinkX 图数据库 | 所有业务实体全量存储 |
| 过程态数据 | 备选方案 | 默认本地缓存，需跨系统共享时入图 |

### 10.2 LinkX 故障降级策略

**决策**：队列异步写入 + 补偿机制（Q1 选项 C）

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│  业务操作   │ ──▶ │ 写入 LinkX  │ ──▶ │  成功？     │ ──▶ │   完成      │
└─────────────┘     └─────────────┘     └──────┬──────┘     └─────────────┘
                            │                   │
                            │                   │ 失败
                            ▼                   ▼
                     ┌─────────────┐     ┌─────────────┐
                     │  写入失败   │ ──▶ │ 写入补偿队列 │
                     └─────────────┘     └──────┬──────┘
                                                │
                                                ▼
                                         ┌─────────────┐
                                         │ 后台补偿任务 │
                                         └──────┬──────┘
                                                │
                                                ▼
                                         ┌─────────────┐
                                         │  重试写入   │
                                         └─────────────┘
```

### 10.3 Part 规格过滤查询策略

**决策**：混合策略（Q2 选项 C）

| 查询类型 | 执行位置 | 说明 |
|---|---|---|
| 简单规格过滤（单维度、单属性） | LinkX 图属性过滤 | 利用图引擎能力 |
| 复杂规格过滤（多维度、聚合） | 本地计算 + LinkX | 先筛选候选集，再本地聚合 |
| 跨 Module 查询 | LinkX 图遍历 | 利用图的多跳能力 |

### 10.4 递归深度限制

**决策**：Module 最大递归深度为 10 层（Q4 决策）

| 限制 | 值 | 说明 |
|---|---|---|
| Module 递归深度 | 10 | 超过时报错，不允许创建 |

### 10.5 业务维度扩展策略

**决策**：使用 BusinessObject + ModuleObjectRelation 实现灵活的维度扩展

- 新增业务维度时，只需定义新的 BusinessObjectType（如 type=COMPLIANCE）
- 然后通过 ModuleObjectRelation 建立模块与业务对象的关联
- 无需修改核心模型和数据库表结构
