## 1. 背景与问题陈述

### 1.1 当前建模立场

依据 [数字产品数据模型 v2.0](./../数字产品数据模型.md)，本系统将产品领域实体按 **Schema on-graph**（图上建模）方式处理：

- **ProductClass**（产品类）：定义为图上的 Schema 节点（`struct_type = PRODUCT_CLASS`），示例：`ROUTER_PLATFORM`（路由器产品平台）
- **PartClass**（部件分类）：定义为图上的 Schema 节点（`struct_type = PART_CLASS`），示例：`router_cpu`（路由器 CPU 分类）
- **Part**（具体部件）：定义为图上的数据节点（`struct_type = PART`），示例：`RTR_CPU_01`（双核 CPU）
- **ProductInstance**（销售产品实例）：定义为图上的数据节点（`struct_type = PRODUCT_INSTANCE`），示例：`ROUTER_01`（低端企业路由器）

其中 **ProductClass** 和 **PartClass** 在图上表达为 Schema（结构定义），**Part** 和 **ProductInstance** 表达为数据实例。Schema 和数据实例均在同一张图上，Schema 定义结构，数据实例填充具体值。

### 1.2 备选建模立场

业界和部分产品数据管理系统存在另一种建模立场：**Template off-graph**（模板离线存储）：

- **第一步**：将产品纯粹作为模板（Template），完全不需要入图，模板存在独立的模板库（如 MetaModule 表）中
- **第二步**：在创建销售产品模型时，才将其定义为真正的图 Schema，但它的很多信息需要从模板中继承
- **第三步**：具体的销售产品实例（SKU）才是真正的数据

### 1.3 问题陈述

**核心问题**：数字产品系统应采用哪种建模立场？

**决策维度**：
1. **标准化问题**：Schema on-graph 如何支撑全公司/全产业的标准化语义统一？Template off-graph 是否带来额外风险？
2. **Schema 膨胀问题**：Schema on-graph 在多产业（10+）场景下，Schema 数量可能达到 1000+，膨胀带来的实际问题是什么？
3. **Part 设计问题**：Part（部件）数量级是 ProductClass 的 10~20 倍，Part 如何建模？Part 属性如何设计？
4. **数据建模综合评估**：两种方案在数据维护、版本管理、跨系统集成上的对比
5. **业界参考**：业界标准做法是什么（eTOM、AT&T/TMF SID、Salesforce CPQ、ORAN、GB/T 等）
6. **业界竞争分析**：各厂商在"标准化与个性化"之间如何取舍

## 2. 方案定义

### 2.1 方案 A：Schema on-graph（现行方案，已采纳）

#### 2.1.1 核心定义

**所有领域实体（图上建模）**：ProductClass、PartClass、Part、ProductInstance 均为图上节点，各自承担不同角色：

| 实体 | 图上角色 | struct_type | 示例 | 说明 |
| --- | --- | --- | --- | --- |
| ProductClass | Schema 节点 | PRODUCT_CLASS | `ROUTER_PLATFORM` | 产品平台骨架，定义可配置结构 |
| PartClass | Schema 节点 | PART_CLASS | `router_cpu` | 部件分类边界 |
| Part | 数据节点 | PART | `RTR_CPU_01` | 具体部件实例，含规格值 |
| ProductInstance | 数据节点 | PRODUCT_INSTANCE | `ROUTER_01` | 可售 SKU，含配置约束 |

#### 2.1.2 图结构示意

```
GES Graph（发布态）
══════════════════════════════════════════════════════════

  【Schema 节点层（定义结构）】

  ┌─────────────────────────────────────────────────────┐
  │  ProductClass: ROUTER_PLATFORM                    │
  │  struct_type = PRODUCT_CLASS                     │
  │  (Schema 定义产品平台骨架)                        │
  └─────────────────────┬───────────────────────────┘
                         │ CONTAINS
                         ▼
  ┌─────────────────────────────────────────────────────┐
  │  PartClass: router_cpu                          │
  │  struct_type = PART_CLASS                       │
  │  (Schema 定义 CPU 分类边界)                       │
  └─────────────────────┬───────────────────────────┘
                         │ CONTAINS
                         ▼
  ┌─────────────────────────────────────────────────────┐
  │  Part: RTR_CPU_01                               │
  │  struct_type = PART                            │
  │  (数据节点，含规格值: core_num=2, bandwidth=10G)  │
  └─────────────────────────────────────────────────────┘


  【数据节点层（填充实例）】

  ┌─────────────────────────────────────────────────────┐
  │  ProductInstance: ROUTER_01                    │
  │  struct_type = PRODUCT_INSTANCE                 │
  │  (数据节点，可售 SKU，含 Part 裁剪约束)           │
  └─────────────────────────────────────────────────────┘
```

#### 2.1.3 Part 的特殊处理

Part 数量级远大于 ProductClass（10~20 倍），Schema on-graph 方案对 Part 采用以下设计策略：

| 策略 | 说明 | 规模预估 |
| --- | --- | --- |
| Part 实例全量入图 | 每个具体 Part（如 RTR_CPU_01）均作为节点存图 | 2,000,000 行 |
| Part 规格值通过 ModuleAttribute 关联 | SPEC_CORE_NUM、SPEC_MAX_BANDWIDTH 等作为 ModuleAttribute 节点，通过 HAS 关系挂载 | ~10,000+ ModuleAttribute |
| Part 与 PartClass 通过 CONTAINS 关系连接 | PartClass 定义候选集，Part 实例通过关系引用 | — |
| Part 按 ProductClass 分区隔离 | 不同产品线的 Part 入不同 Graph，避免跨产业污染 | 按 product_category 隔离 |

### 2.2 方案 B：Template off-graph（备选方案）

#### 2.2.1 核心定义

**模板与 Schema 分离**：ProductClass / PartClass 仅作为模板（Template）存在于独立的模板库中，不入图；只有 ProductInstance（SKU）才入图作为 Schema。

| 步骤 | 模板角色 | 图上角色 | 示例 |
| --- | --- | --- | --- |
| 第一步 | ProductClass 仅为模板，存 MetaModule 表，不入图 | — | `ROUTER_PLATFORM_TEMPLATE`（MetaModule） |
| 第二步 | PartClass 仅为模板，存 MetaModule 表 | — | `router_cpu_TEMPLATE`（MetaModule） |
| 第三步 | 创建销售产品模型时，将模板继承为图 Schema | ProductInstance 作为 Schema 节点入图 | `ROUTER_01`（图上节点） |
| — | Part 实例 | Part 节点入图（继承 PartClass 模板信息） | `RTR_CPU_01` |

#### 2.2.2 图结构示意

```
MetaModule（模板库，独立于图）
═════════════════════════════════════

  ┌─────────────────────────────────────────────────┐
  │  MetaModule: ROUTER_PLATFORM_TEMPLATE           │
  │  struct_type: PRODUCT_CLASS_TEMPLATE           │
  │  (模板定义，存 PG 元数据表，不入图)              │
  └─────────────────────────────────────────────────┘
                        │ 继承
                        ▼
  ┌─────────────────────────────────────────────────┐
  │  MetaModule: router_cpu_TEMPLATE               │
  │  struct_type: PART_CLASS_TEMPLATE             │
  │  (模板定义，存 PG 元数据表，不入图)              │
  └─────────────────────────────────────────────────┘


GES Graph（发布态，仅 SKU 入图）
══════════════════════════════════════════════════════════

  ┌─────────────────────────────────────────────────────┐
  │  ProductInstance: ROUTER_01                       │
  │  struct_type = PRODUCT_INSTANCE                  │
  │  (SKU 入图，继承 ROUTER_PLATFORM_TEMPLATE 模板)     │
  │  (含 Part 裁剪约束、规格覆盖等)                   │
  └─────────────────────────────────────────────────────┘

  ┌─────────────────────────────────────────────────────┐
  │  Part: RTR_CPU_01                                │
  │  struct_type = PART                             │
  │  (Part 实例入图，继承 router_cpu_TEMPLATE 模板)     │
  └─────────────────────────────────────────────────────┘
```

#### 2.2.3 Part 的特殊处理

方案 B 对 Part 的处理：

| 策略 | 说明 |
| --- | --- |
| PartClass 模板不入图 | `router_cpu_TEMPLATE` 存 MetaModule 表 |
| Part 实例入图，继承模板信息 | `RTR_CPU_01` 入图，从 `router_cpu_TEMPLATE` 继承结构 |
| Part 规格通过模板继承获取 | Part 实例本身不存规格值，通过模板继承链路解析 |

## 3. 四维度综合分析

### 3.1 数据建模维度

#### 3.1.1 Part 设计综合对比

Part 是本系统的规模最大实体（2,000,000 行），是方案选型的关键变量。

| 评估维度 | 方案 A（Schema on-graph） | 方案 B（Template off-graph） | 评估结论 |
| --- | --- | --- | --- |
| **Part 入图方式** | Part 实例（RTR_CPU_01）作为图上数据节点入图，通过 HAS 关系关联规格值 | Part 实例入图，继承 PartClass 模板结构（模板信息通过元数据关联） | **方案 A 规格值直接可查询；方案 B 需二次 JOIN 模板** |
| **Part 与 PartClass 关系** | Part 通过 CONTAINS 关系引用 PartClass（两者均为图上节点） | Part 入图，PartClass 仅存模板表（通过 meta_id 引用） | **方案 A 关系天然可遍历；方案 B 图上缺少 Part→PartClass 边** |
| **Part 规格值存储** | ModuleAttribute 作为独立节点，通过 HAS 关系挂载到 Part 上（可独立查询） | Part 实例通过元数据引用 PartClass 模板，模板中定义规格 Schema（运行时展开） | **方案 A 查询灵活；方案 B 结构紧凑但查询路径长** |
| **Part 规模对图的影响** | 2,000,000 个 Part 节点全部入图，图规模较大但可分区隔离 | 2,000,000 个 Part 节点入图（与方案 A 相同），PartClass 模板不入图节省少量节点 | **Part 规模影响相同；方案 B 节省 PartClass 节点（~100,000 个）但引入模板引用复杂度** |
| **Part 跨产业共享** | 同一个 Part 可通过多重 CONTAINS 关系被多个 ProductClass 引用（Part 节点唯一，引用关系多元） | 同一个 Part 可被多个 ProductInstance 继承（Part 实例唯一，继承关系通过模板链路） | **方案 A 多重引用更直观；方案 B 继承链路更长** |
| **Part 属性个性化** | 每个 Part 节点有独立属性值（core_num=2、bandwidth=10G），个性化表达充分 | Part 实例从模板继承属性 Schema，属性值在实例层填写（模板定义规格类型，实例提供具体值） | **两者均可充分表达个性化；方案 A 直接，方案 B 结构化程度更高** |
| **Part 版本管理** | Part 变更通过快照（id=UUID 新行）实现版本历史，每次变更可追溯 | Part 变更同样通过快照实现，但模板变更会影响所有继承该模板的 Part 实例（模板版本耦合） | **方案 A 版本独立性好；方案 B 存在模板-实例版本耦合风险** |
| **Part 维护入口** | Part 可独立维护（创建/修改/删除），PartClass 定义候选集边界 | Part 通过模板继承链路维护，PartClass 变更可能影响所有继承实例 | **方案 A 维护更独立；方案 B 维护需要考虑模板影响范围** |

#### 3.1.2 数据维护综合对比

| 评估维度 | 方案 A（Schema on-graph） | 方案 B（Template off-graph） | 评估结论 |
| --- | --- | --- | --- |
| **维护入口统一性** | 所有实体（ProductClass / PartClass / Part / ProductInstance）均通过 MS 服务维护，图上节点统一 | ProductInstance 和 Part 入图维护；ProductClass / PartClass 仅在模板库维护，入口分裂 | **方案 A 入口统一；方案 B 需维护两套入口（图 + 模板表）** |
| **ProductClass 变更影响** | ProductClass 节点变更影响 CONTAINS 关系（子节点范围变化），影响可控 | ProductClass 作为模板变更，所有继承的 ProductInstance 均受影响（模板-实例耦合） | **方案 A 影响范围更局部；方案 B 存在模板变更级联风险** |
| **Part 变更影响** | Part 节点变更独立，不影响 ProductClass / PartClass 结构 | Part 变更独立（与方案 A 相同），但继承链路需要运行时展开 | **两者均可独立维护；方案 A 更直接** |
| **版本追溯** | 每个实体独立快照（id=UUID 新行），版本链路清晰 | ProductInstance 快照包含模板版本引用，追溯链路包含模板历史 | **方案 A 追溯更直接；方案 B 需额外追踪模板版本** |
| **Part 候选集管理** | PartClass 定义候选集边界（CONTAINS 关系的 min/max cardinality），Part 实例通过关系引用 | PartClass 模板定义候选集 Schema，ProductInstance 通过继承关系获取候选集（运行时展开） | **方案 A 图上直接可查候选集；方案 B 需要遍历继承链路** |
| **跨 PartClass 的 Part 共享** | 同一个 Part 可同时被多个 PartClass 引用（Part 节点唯一，多条 CONTAINS 关系），跨类共享直观 | Part 实例独立维护，跨类共享需要通过 PartClass 模板组合实现（共享链路长） | **方案 A 共享更直观；方案 B 需要额外设计共享机制** |
| **未来扩展性** | ProductClass / PartClass / Part / ProductInstance 均为图上节点，可随时新增 struct_type 扩展维度 | ProductClass / PartClass 仅存模板，新增 struct_type 只需扩展 MetaModule 表，不影响图结构 | **方案 B 在 struct_type 扩展上更轻量；但方案 A 的扩展成本也可接受** |

#### 3.1.3 ProductInstance 定位对比

| 评估维度 | 方案 A（Schema on-graph） | 方案 B（Template off-graph） | 评估结论 |
| --- | --- | --- | --- |
| **ProductInstance 图上角色** | 数据节点（struct_type=PRODUCT_INSTANCE），含 Part 裁剪约束（enabled_parts/disabled_parts）和规格覆盖（spec_overrides） | 图上 Schema（继承 ProductClass 模板），含配置约束 | **两者均入图；方案 A 直接表达约束，方案 B 通过继承隐式表达约束** |
| **ProductInstance 与 ProductClass 关系** | INSTANTIATES 边（ROUTER_PLATFORM → ROUTER_01），图上显式可遍历 | 继承关系（ROUTER_PLATFORM_TEMPLATE → ROUTER_01），通过模板链路隐式表达 | **方案 A 关系显式可查；方案 B 需要追踪模板链路** |
| **ProductInstance 配置查询** | 配置 Agent 直接查询 ProductInstance 节点及其 enabled_parts 边属性，裁剪结果直接可读 | 配置 Agent 查询 ProductInstance 节点，通过继承链路解析 Part 候选集（需要聚合模板+实例数据） | **方案 A 查询更直接；方案 B 需要额外聚合逻辑** |
| **多 SKU 场景（ROUTER_01/02/03）** | 每个 SKU 为独立 ProductInstance 节点（ROUTER_01、ROUTER_02、ROUTER_03），图上直接可区分 | 每个 SKU 继承模板后作为独立 Schema 入图（与方案 A 结构相同，但模板信息独立存储） | **两者均可支持多 SKU；方案 A 结构更简洁** |

### 3.2 业界参考维度

#### 3.2.1 主流标准与框架参考

**① eTOM（增强的电信运营图）/ TMF SID（信息框架）**

- eTOM 和 TMF SID 对产品的建模采用 **分层抽象**：Product（产品）→ Service（服务）→ Resource（资源）
- 其中 Product 作为 **服务提供层面的 Schema**，服务实例（Service Instance）与产品实例（Product Instance）分开建模
- **对标分析**：本系统的 ProductClass 对应 eTOM 的 Product Specification，ProductInstance 对应 Service Instance。eTOM 体系**不主张将 Template 离线存储**，而是将 Product Specification 视为图中节点，通过版本化管理区分不同迭代
- **对方案 A 的支撑**：Schema on-graph 与 eTOM 分层建模一致，ProductClass 作为 Specification 入图是业界标准做法

**② AT&T/TMF 集团级产品数据模型（GB/T 9621-2019 对标）**

- GB/T 9621-2019（电信产品目录规范）对产品的建模要求：产品目录项（Product Catalog Item）必须有 **全局唯一标识**和 **标准属性集合**
- **标准化要求**：ProductClass/PartClass 的 code 必须是全局唯一（不受产业/产品线限制），这是跨系统互通的基础
- **对方案 A 的支撑**：Schema on-graph 天然支撑全局唯一 code（每个节点有独立 code 字段），跨系统集成时直接引用 code，无需模板库映射
- **对方案 B 的风险**：Template off-graph 需要维护模板库与图上节点的映射关系，跨系统集成时需要额外的映射表（模板 code → 图上节点 ID）

**③ Salesforce CPQ（Configure-Price-Quote）**

- Salesforce CPQ 采用 **模板驱动 + 实例化** 建模：
  - **Product Template**：定义产品可配置项（Rules、Constraints、Options）
  - **Product Bundle**：模板组合
  - **Quote Line Item**：实例化结果
- CPQ 的 Product Template **不入图**，存储在 CPQ 产品表（类似 MetaModule 表），通过 Instance 关系引用
- **对方案 B 的支撑**：Template off-graph 在 CPQ 类系统中是成熟实践，但 CPQ 的场景是"配置-报价"，与数字产品系统的"产品结构定义"有本质差异
- **关键差异**：CPQ 的 Product Template 描述的是"可配置规则"，而本系统的 ProductClass 描述的是"产品结构定义"。数字产品系统的结构定义需要被下游系统（财务、PLM、ERP）直接引用，**结构定义的标准化比模板的灵活性更重要**

**④ ORAN（开放无线接入网络）**

- ORAN 联盟对网络产品的建模采用 **分层模型**：Radio Unit（设备）→ Network Function（功能）→ Service（服务）
- ORAN 的产品建模 **强调 Schema on-graph**：每个层级均有独立的 YANG 模型（对应 Schema），实例通过数据节点表达
- **对方案 A 的支撑**：Schema on-graph 与 ORAN 分层建模一致，层级之间通过关系边连接（图结构天然支持层级遍历）

**⑤ 华为 ICT 产品建模实践**

- 华为内部产品数据系统（如 MTX、PDM）对产品采用 **三层建模**：
  - **规格书（Spec）**：定义产品规格（对应 ProductClass/PartClass 的 SPEC 维度）
  - **物料（BOM）**：定义部件结构（对应 Part 的 BOM 层级）
  - **产品（Product）**：可售 SKU（对应 ProductInstance）
- 华为产品数据系统**不将规格书作为模板离线存储**，而是作为图中节点，通过版本化管理
- **对方案 A 的直接支撑**：Schema on-graph 与华为产品数据建模实践一致

#### 3.2.2 业界方案对比矩阵

| 框架/系统 | 产品建模立场 | Schema 存储位置 | Part 建模方式 | 是否支撑全局标准化 | 对方案 A 的支撑度 | 对方案 B 的支撑度 |
| --- | --- | --- | --- | --- | --- | --- |
| eTOM / TMF SID | Schema on-graph | 图上节点（Product Specification） | Resource 分层 | ✅ 是（全局唯一标识） | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ |
| GB/T 9621-2019（电信产品目录） | Schema on-graph | 目录项（全局唯一 code） | BOM 分层 | ✅ 是（全局标准化） | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ |
| Salesforce CPQ | Template off-graph | CPQ 产品表（Template） | Bundle 组合 | ❌ 否（模板私有） | ⭐⭐ | ⭐⭐⭐⭐ |
| ORAN 网络建模 | Schema on-graph | YANG 模型（对应 Schema 节点） | 分层节点 | ✅ 是（层级标准化） | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ |
| 华为 ICT 产品数据 | Schema on-graph | 规格书/BOM 入系统（对应 Schema） | BOM 物料分层 | ✅ 是（全局标准化） | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ |
| 业界平均值 | **Schema on-graph 为主** | — | **BOM 分层 + Schema on-graph** | **✅ 是** | **⭐⭐⭐⭐** | **⭐⭐⭐** |

**结论**：主流电信/ICT 行业标准（eTOM、TMF SID、GB/T、ORAN、华为实践）均采用 **Schema on-graph** 方案。Template off-graph 主要存在于 CPQ/电商配置系统（场景不同）。

### 3.3 业界竞争分析维度

#### 3.3.1 数字主线（Digital Thread）领域的竞争格局

数字产品系统构建的是 **数字主线（Digital Thread）**：从产品规划 → 设计 → 制造 → 服务，覆盖全生命周期。数字主线的核心挑战是**标准化与个性化的平衡**。

**竞争者分层**：

| 竞争者类型 | 代表厂商 | 产品建模立场 | 标准化策略 | 个性化策略 |
| --- | --- | --- | --- | --- |
| **第一梯队（PLM 巨头）** | Siemens Teamcenter、PTC Windchill、Dassault 3DEXPERIENCE | Schema on-graph + Template off-graph 混合 | 产品结构标准化（BOM 模板），全局 code体系 | 配置器驱动个性化（CPQ） |
| **第二梯队（电信设备商）** | 华为 MTX、中兴 ZTE PDM、爱立信产品系统 | Schema on-graph 为主 | 产品族标准化（GB/T、eTOM），Part code 全局唯一 | 配置规则驱动个性化 |
| **第三梯队（云原生产品系统）** | Salesforce CPQ、Configure One、Apttus | Template off-graph 为主 | 模板标准化（行业模板库） | 配置器 + 规则引擎个性化 |
| **第四梯队（产业互联网平台）** | Bosch IoT Suite、Siemens MindSphere、树根互联 | Schema on-graph 为主（混合） | 设备模型标准化（数字孪生） | 租户个性化配置 |

#### 3.3.2 标准化与个性化的博弈分析

**标准化收益曲线**（各产业 Schema 数量 vs 标准化收益）：

```
标准化收益
    ▲
    │                      ╱
    │                   ╱
    │                ╱
    │             ╱
    │          ╱
    │       ╱
    │    ╱
    │ ╱
    └──────────────────────────► Schema 数量
       1     10    100   1000
       
       A区：Schema 少量，标准化收益低（ROI 不划算）
       B区：Schema 中等，标准化收益最高（边际收益 > 边际成本）
       C区：Schema 大量，标准化收益递减（过度标准化抑制灵活性）
```

**Schema 膨胀的临界点分析**：

| 场景 | Schema 数量 | Schema on-graph 收益 | Schema off-graph 收益 | 推荐方案 |
| --- | --- | --- | --- | --- |
| 单产业（路由器） | ~10 个 ProductClass + ~100 个 PartClass | 高（标准化覆盖完整，ROI 正） | 中（模板复用价值一般） | **方案 A** |
| 2~5 产业 | ~50 个 ProductClass + ~500 个 PartClass | 高（跨产业标准化价值显现） | 中（模板跨产业复用有价值） | **方案 A** |
| 5~10 产业 | ~100 个 ProductClass + ~1,000 个 PartClass | **临界点**（标准化价值高，但 Schema 管理成本上升） | 中（模板跨产业复用价值显著） | **方案 A + PartClass 分区隔离** |
| 10+ 产业 | ~1,000 个 ProductClass + ~10,000 个 PartClass | 中（Schema 膨胀成本开始显现） | 高（模板复用价值最大化） | **方案 B 或混合方案** |

**Part 规模的关键影响**：

Part 数量是 ProductClass 的 10~20 倍，这是 Schema 膨胀的核心驱动力。

| 产业数 | ProductClass | PartClass | Part（预估） | Schema on-graph 图节点总数 | 临界判断 |
| --- | --- | --- | --- | --- | --- |
| 1 | ~10 | ~100 | ~2,000 | ~2,110 | ✅ 无临界问题 |
| 5 | ~50 | ~500 | ~10,000 | ~10,550 | ✅ 无临界问题 |
| 10 | ~100 | ~1,000 | ~20,000 | ~21,100 | ⚠️ Part 规模接近 2M 临界（需分区） |
| 20 | ~200 | ~2,000 | ~40,000 | ~42,200 | ⚠️ Schema 膨胀成本显现 |

**结论**：在 10 个产业以内（约 21,000 个节点），Schema on-graph 无明显临界问题；超过 10 个产业后，需要引入 **Part 分区隔离策略**（按 product_category 分 Graph），而非迁移到 Template off-graph。

#### 3.3.3 跨产业标准化的竞争策略

**竞争对手的标准化策略**：

| 策略 | 代表厂商 | 手段 | 效果 |
| --- | --- | --- | --- |
| **Code 标准化** | 华为 MTX、eTOM 体系 | ProductClass code 全局唯一，跨产业互通 | 财务系统、PLM 系统可直接引用 |
| **模板标准化** | Salesforce CPQ、Configure One | 行业模板库（电信/医疗/汽车） | 模板复用，交付效率提升 |
| **数据分区标准化** | Bosch IoT Suite | 按产业/产品线分区，不同分区 Schema 隔离 | 跨区不污染，区内标准化 |
| **混合策略** | Siemens Teamcenter | Schema on-graph + Template off-graph 混合 | 兼顾标准化与灵活性 |

**本系统的竞争策略选择**：

方案 A（Schema on-graph）+ **Part 分区隔离策略** = 兼顾标准化与规模可扩展性

- ✅ 支撑全局 Code 标准化（跨系统互通）
- ✅ Schema on-graph 与主流电信标准对齐
- ✅ 通过 Graph 分区（product_category）控制 Schema 膨胀
- ⚠️ Part 规模（2,000,000 行）需通过分区隔离控制（按产业/产品线）

### 3.4 Part 设计专项分析

#### 3.4.1 Part 的三层角色

Part 在数字产品系统中承担 **三层角色**，每层需要不同的建模策略：

| Part 角色 | 说明 | 建模策略 | 示例 |
| --- | --- | --- | --- |
| **PartTemplate（部件模板）** | 部件的分类边界，定义"有哪些属性" | PartClass 节点（Schema on-graph） | `router_cpu`（路由器 CPU 分类） |
| **PartSpec（部件规格）** | 部件的具体规格值，定义"属性值是多少" | ModuleAttribute 节点 + HAS 关系 | `SPEC_CORE_NUM=2`、`SPEC_MAX_BANDWIDTH=10Gbps` |
| **PartInstance（部件实例）** | 部件的具体实例，定义"哪个具体部件" | Part 节点（数据 on-graph） | `RTR_CPU_01`（双核 CPU 实例） |

#### 3.4.2 Part 属性设计方案

**Part 属性分为两类**：

| 属性类型 | 特点 | 建模策略 | 示例 |
| --- | --- | --- | --- |
| **结构属性** | Part 的分类边界属性（如 CPU 分类名称、端口类型） | PartClass 节点属性（Schema 层） | `router_cpu` 的 `name="路由器 CPU"`、`category="computing"` |
| **规格属性** | Part 的具体规格值（如核心数、带宽） | ModuleAttribute 节点 + HAS 关系（数据层） | `SPEC_CORE_NUM=2`、`SPEC_MAX_BANDWIDTH=10Gbps` |
| **业务属性** | Part 的业务上下文（如供应商、成本） | Part 节点属性（数据层） | `supplier="Intel"`、`cost=1500 CNY` |

**推荐方案**（Schema on-graph 体系下）：

```
图上节点（数据层）
════════════════════════════════════════════════════

  ┌─────────────────────────────────────────────────────────────┐
  │  Part: RTR_CPU_01                                        │
  │  struct_type = PART                                       │
  │  code = "RTR_CPU_01"                                     │
  │  name = "双核 CPU"                                        │
  │  (Part 节点，存结构属性和业务属性)                         │
  └────────────────────────┬──────────────────────────────────┘
                           │ HAS（ModuleStructAttributeRelation）
                           ▼
  ┌─────────────────────────────────────────────────────────────┐
  │  ModuleAttribute: SPEC_CORE_NUM                            │
  │  attr_type = SPEC                                        │
  │  (规格属性节点，存规格定义 Schema)                          │
  └────────────────────────┬──────────────────────────────────┘
                           │ 属性值
                           ▼
                    attr_value = 2  (core)
```

**Part 属性设计的核心规则**：

1. **Part 节点只存"是什么"**：code、name、supplier、cost 等固有属性
2. **ModuleAttribute 节点存"规格值"**：通过 HAS 关系挂载到 Part 上（规格值作为独立节点，便于跨 Part 复用）
3. **PartClass 节点定义候选集边界**：通过 CONTAINS 关系约束 Part 候选集范围

#### 3.4.3 Part 规模控制策略

| 策略 | 适用规模 | 手段 | 效果 |
| --- | --- | --- | --- |
| **按 product_category 分区** | 10 个产业以内 | 每个产业一个 Graph，Part 按产业分区隔离 | 单一 Graph 不超 50,000 节点 |
| **按 PartClass 分区** | 单一产业内 Part 超过 100,000 | 不同 PartClass 入不同 Graph | 避免单 Graph 节点过密 |
| **按时间分表** | Part 总数超过 2,000,000 | PG 按年份分表（obj_table_004 按 created_year） | 突破 PG 单表 500 万行上限 |

## 5. 决策

### 5.1 最终方案：Schema on-graph（方案 A）+ 扩展规则

**采纳方案 A**，并制定以下扩展规则应对规模化挑战：

#### 扩展规则 1：Graph 分区隔离（针对 Schema 膨胀）

> **规则**：当产业数 ≥ 10 或单 Graph 节点数 ≥ 50,000 时，按 `product_category` 分 Graph。

```
Graph: publish_graph_router（路由器产业）
  ROUTER_PLATFORM (ProductClass)
  router_cpu (PartClass)
  RTR_CPU_01 (Part) ...
Graph: publish_graph_server（服务器产业）
  SERVER_PLATFORM (ProductClass)
  server_cpu (PartClass)
  SRV_CPU_01 (Part) ...
```

**分区依据**：product_category（产业分类），不同产业的 ProductClass / PartClass / Part 分区隔离，跨产业 Part 共享通过 Part 节点唯一 + 多条 CONTAINS 关系实现。

#### 扩展规则 2：Part 分区策略（针对 Part 规模）

> **规则**：当 Part 总数 ≥ 2,000,000 时，按 `part_category` 分区入不同 Graph。

**分区策略**：
- 按 PartClass 分区：不同 PartClass 入不同 Graph（CPU 入 router_graph、内存入 server_graph）
- 按时间分表：PG 按 `created_year` 分表（obj_table_004 按年份分区）

#### 扩展规则 3：PartClass 模板标准化（针对 Part 数量 10~20 倍问题）

> **规则**：PartClass 定义候选集边界，Part 实例是具体的部件节点，两者通过 CONTAINS 关系连接。

**标准化的 Part 层级**：

| Part 层级 | 角色 | 入图方式 | 示例 |
| --- | --- | --- | --- |
| PartClass | 部件分类边界（定义候选集） | Schema 节点 | `router_cpu` |
| Part | 具体部件（PartClass 的实例） | 数据节点 | `RTR_CPU_01` |

**Part 与 PartClass 的关系**：CONTAINS（PartClass → Part），Part 通过 CONTAINS 关系引用 PartClass，PartClass 约束 Part 候选集范围（min/max cardinality）。

### 5.2 关键设计决策

| 决策 ID | 决策内容 | 依据 |
| --- | --- | --- |
| D-001 | **ProductClass 和 PartClass 均作为 Schema 节点入图**，不在模板库中独立存储 | Schema on-graph 与主流电信标准（eTOM/TMF SID/GB/T/ORAN）一致；跨系统互通天然支撑 |
| D-002 | **ProductInstance 作为数据节点入图**，通过 INSTANTIATES 边引用 ProductClass | SKU 直接入图，配置 Agent 可直接查询（无需模板链路解析） |
| D-003 | **Part 作为数据节点入图**，通过 ModuleAttribute 关联规格值，PartClass 定义候选集边界 | Part 节点存结构属性，ModuleAttribute 节点存规格值，Part 规模（2M）可通过 Graph 分区控制 |
| D-004 | **Part 按 product_category 分 Graph**（当产业数 ≥ 10 或单 Graph ≥ 50,000 节点时） | 控制 Schema 膨胀，避免单 Graph 节点过密 |
| D-005 | **Part 按 PartClass 分区入不同 Graph**（当 Part 总数 ≥ 2,000,000 时） | 突破 PG 单表 500 万行上限，通过 Graph 分区隔离 Part 规模 |
| D-006 | **ProductClass code 全局唯一**（跨产业唯一） | 支撑全公司/全产业标准化，跨系统互通（财务系统、PLM/ERP 直接引用 ProductClass code） |
| D-007 | **Part 节点 code 全局唯一**（跨产业唯一） | 同一个 Part 可被多个 ProductClass 引用（如通用 CPU），跨产业共享无需复制节点 |
| D-008 | **PartClass 定义候选集边界**（CONTAINS 关系的 min/max cardinality） | 图上直接可查 Part 候选集，无需模板链路解析 |

## 6. 风险与应对

| 风险 | 严重度 | 缓解策略 |
| --- | --- | --- |
| **Schema 膨胀（>10 产业）** | 🟡 中等 | 引入 Graph 分区策略（按 product_category 分 Graph），每 Graph 不超 50,000 节点 |

| **Graph 分区后跨区查询** | 🟢 低 | 通过 QS 聚合层跨 Graph 查询（配置 Agent 通过 QS 查询，QS 内部跨 Graph 聚合） |

## 7. 验收标准

| 验收用例 | 场景 | 期望结果 |
| --- | --- | --- |
| EU-1 | ProductClass（ROUTER_PLATFORM）和 PartClass（router_cpu）均作为图上节点存在 | LinkX 查询 `MATCH (n {struct_type: 'PRODUCT_CLASS'})` 返回 ROUTER_PLATFORM；`MATCH (n {struct_type: 'PART_CLASS'})` 返回 router_cpu |

| EU-4 | ProductInstance（ROUTER_01）通过 INSTANTIATES 边引用 ProductClass（ROUTER_PLATFORM） | LinkX 查询 `MATCH (pc)-[:INSTANTIATES]->(pi)` 返回 ROUTER_PLATFORM → ROUTER_01 关系 |

| EU-7 | Part 按 product_category 分区（>10 产业场景） | 不同产业的 Part 入不同 Graph（如 router_graph / server_graph），单 Graph 节点数 < 50,000 |
