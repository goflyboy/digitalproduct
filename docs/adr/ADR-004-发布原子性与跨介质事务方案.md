## 1. 背景与问题

### 1.1 业务场景

数据发布服务（PS.PublishOrchestrator）需要把维护态数据按"节点 + 边属性 + 关系"三源聚合后，**一次性**写入发布态 LinkX 的 `publish_graph`。这个动作涉及三个写入目标：

- **PG 通用表**：`obj_table_001~020`、关系独立表 `rel_module_*_relation`
- **LinkX 维护态图**：`maintain_graph_upstream`（UPSTREAM 属性）
- **LinkX 发布态图**：`publish_graph`（发布后读写给下游 Agent 消费）

### 1.2 核心矛盾

架构文档 v1.14 已经把"三源聚合"画清楚了（§6.2.8 UC-B1b 时序图的 Step 2.5 + Step 3），但**实现层 3 个关键能力尚未明确**：

#### 矛盾 1：发布原子性——"要么全成功，要么全失败"

发布过程涉及多个写操作（PG + LinkX），任一环节失败可能产生"维护态标记为 PUBLISH 但发布态数据不完整"的脏状态。常见失败模式：

- PG 标记成功（`UPDATE obj_table_002 SET _maintenance_state='PUBLISH'`）后，LinkX 写入失败 → **维护态已标 PUBLISH，发布态没有**
- LinkX 写入部分成功（ProductInstance 节点成功、Part 节点失败）→ **图不一致**
- 多 Part 节点批量写入 LinkX 中途网络中断 → **部分 Part 节点孤立**

#### 矛盾 2：跨介质事务——PG 和 LinkX 没有原生 2PC

PG 事务和 LinkX（GES 持久化版）事务**无法跨介质两阶段提交**（2PC 不支持异构介质）。架构文档 §3.5.2 OPEN-25 仅覆盖了"PG 单事务"与"PG+TM 应用层补偿"，**没有覆盖"PG + LinkX 异构事务"**。

#### 矛盾 3：LinkX 写权限——"应有但未画"

发布态图 `publish_graph` 的写权限管理在架构文档里**从未明确**：

- 谁有权限写 `publish_graph`？只 PS？还是 MS 也能写？
- 写权限如何隔离？LinkClient 的 ACL 配置？还是 GES 的 Security Authority？
- 维护态图 `maintain_graph_upstream` 的写权限呢？只 UAS？还是 TM 直接写？
- 与 §3.4 "发布是维护态→发布态的唯一通道（PS 独家写入 publish_graph）" 配套的权限配置在哪里？

### 1.3 问题陈述

| 编号 | 问题 |
| --- | --- |
| **Q1** | 发布过程的"PG + LinkX"跨介质原子性如何保证？允许"部分成功"吗？ |

## 2. 候选方案（待 §3 决策）

### 2.1 发布原子性方案候选

**方案 A：SAGA + 补偿事务（推荐）**

- 发布操作拆成 SAGA：Step1 写 PG 状态标记 → Step2 写 LinkX publish_graph → Step3 写 LinkX publish_graph 边
- 每步独立提交，每步成功更新 SAGA 进度（PG 维护一张 `publish_saga_log` 表）
- 任意一步失败，按 SAGA 进度反向补偿：
  - Step3 失败 → 回滚 Step3 已写边
  - Step2 失败 → 回滚 Step2 已写节点 + 回滚 Step1 PG 状态
  - Step1 失败 → 直接放弃（SAGA 未进入主流程）
- **优点**：无 2PC，支持长时间运行，可补偿
- **缺点**：补偿路径多，需要幂等设计；要新增 `publish_saga_log` 表

**方案 B：本地消息表（事件溯源）**

- 发布操作触发 `PublishedEvent` 消息，写入 `event_outbox` 表（PG）+ 同一个本地事务
- 后台 EventPublisher 消费 `event_outbox`，逐事件调 LinkX API 写入
- **优点**：天然解耦，与发布逻辑无关的事件机制
- **缺点**：不能保证"发布操作即生效"，要等消费循环；不解决 LinkX 部分写入问题

**方案 C：2PC / XA（不推荐）**

- 试图让 PG + LinkX 共用一个 2PC 协调器
- **否决**：GES 持久化版不支持 XA 接口，2PC 不可行

### 2.2 LinkX 写权限方案候选

**方案 X：GES Security Authority（推荐）**

- 在 GES 控制台为 `publish_graph` / `maintain_graph_upstream` 各配置一套 Security Authority
- `publish_graph`：只授权给一个服务账号 `dp-publish-service`，LinkClient 内部用这个账号访问
- `maintain_graph_upstream`：只授权给一个服务账号 `dp-maintenance-service`，LinkClient 内部用这个账号访问
- DPWebsite 通过 UAS 调任意写操作时，UAS 用对应账号代理（MANUAL → dp-maintenance-service / UPSTREAM → dp-maintenance-service / PUBLISH → dp-publish-service）
- **优点**：权限在 GES 控制层强制，应用层无法绕过；权限回收是运维操作

**方案 Y：LinkClient 路由拦截（不推荐作为唯一方案）**

- LinkClient 内部按 graph 名称 + 操作类型判断："POST /graphs/publish_graph/vertices" 必须来自 PS
- **否决**：仅靠应用层拦截，一旦 LinkClient 被绕过就失效；需要 X 兜底

**方案 Z：双层（GES + LinkClient 双重）—— 推荐最终态**

- GES 控制层用 Security Authority 强制隔离（主防线）
- LinkClient 在 SDK 层做"互斥检查"（次防线，给开发者看错误信息更友好）
- **优点**：主防+次防，符合"Defense in Depth"

### 2.3 部分发布回滚候选

**方案 α：基于 publish_run_id 的回滚**

- PS 在每次发布时生成 `publish_run_id`（UUID），写入 `publish_saga_log`
- LinkX 写入时**带 `publish_run_id` 属性**（节点/边都带）
- 回滚 API：`rollbackByRunId(runId)` → LinkX 查询 `publish_run_id = runId` 的所有节点/边 → 批量删除
- **优点**：定位精准，不影响其他发布批次
- **缺点**：LinkX 需要支持"按属性批量删除"（GES 持久化版支持）

**方案 β：基于 _maintenance_state 的回滚**

- 不回滚，让用户重新发布新版覆盖
- **否决**：违反"全成功或全失败"原则

## 4. 推荐方案（需用户决策）

### 4.1 发布原子性

[FRAME] **推荐方案 A（SAGA + 补偿）**，理由：
1. GES 持久化版无 XA 接口，2PC 不可行，本地消息表又不能解决 LinkX 部分写入问题
2. 数字产品发布是"低频高价值"操作（一天几百次发布 vs 每秒上千次读取），SAGA 的异步补偿开销可接受
3. 需要新增 `publish_saga_log` 表（PG），记录每次发布的步骤进度

[FRAME] **关联子决策**：
- 幂等键设计：**OPEN-Q8.2 待定**
- 跨介质协调器：**OPEN-Q8.3 待定**

### 4.2 LinkX 写权限

[FRAME] **推荐方案 Z（GES + LinkClient 双重）**：
- **主防线**：GES Security Authority 控制——`publish_graph` 仅 `dp-publish-service` 账号可写；`maintain_graph_upstream` 仅 `dp-maintenance-service` 账号可写
- **次防线**：LinkClient 路由拦截——SDK 层按 graph 名 + 调用者服务 ID 校验
- 理由：Defense in Depth；GES 主防线保证即使 LinkClient 被绕过也不会越权

### 4.3 部分发布回滚

[FRAME] **推荐方案 α（按 `publish_run_id` 回滚）**：
- 每个发布批次带 `publish_run_id`（UUID），写入 LinkX 节点 / 边的属性
- PS 暴露 `rollbackByRunId(runId)` API
- LinkX 按 `publish_run_id = ?` 查询 + 批量删除

## 5. 验收用例（待 §3 决策后细化）

| ID | 场景 | 期望 |
| --- | --- | --- |
| AC-1 | 正常发布（PG + LinkX 都成功） | `publish_saga_log` 状态=SUCCESS，`_maintenance_state=PUBLISH`，LinkX 写入完整图 |
| AC-2 | 发布中 LinkX 写入失败（网络） | SAGA 触发补偿；`publish_saga_log` 状态=FAILED + 补偿记录；维护态数据 `_maintenance_state` 保留 DRAFT |
| AC-3 | 二次重试（相同 `publish_run_id`） | 幂等；不重复写入；SAGA 进度继续 |
| AC-4 | 部分发布回滚（按 `publish_run_id`） | LinkX 中所有 `publish_run_id = X` 的节点 + 边被删除；PG 中 `_maintenance_state` 回滚到 DRAFT |
| AC-5 | MS 误调 publish_graph 写入接口 | GES Security Authority 拒绝（401/403）；LinkClient 拦截 + 友好错误 |
| AC-6 | 非 `dp-publish-service` 账号尝试写 `publish_graph` | GES 拒绝；审计日志记录 |
| AC-7 | 回滚过程中 LinkX 删除失败 | 重试 + 报警；不丢审计 |

## 9. 附录 B：术语表

| 术语 | 定义 |
| --- | --- |
| **跨介质事务** | 涉及两个不同存储介质（PG + LinkX）的事务，无法用单一事务保证原子性 |
| **SAGA** | 一组本地事务 + 补偿事务的长事务模式，每步独立提交，失败回滚补偿 |
| **publish_run_id** | 每次发布生成的 UUID，作为发布批次的幂等键 + 回滚定位键 |
| **GES Security Authority** | 华为云 GES 图引擎的权限控制机制，按账号 / 角色授权 graph 操作 |
| **Defense in Depth** | 多层防御原则，本 ADR 中指 GES 主防线 + LinkClient 次防线 |
